Why

People can react to posts, comments, and post photos, and can reshare a friend’s post, but the original owner has no activity alert for any of those actions. The Notifications page already supports real-time, unread-counted activity with deep links; this work completes that loop.

What

Add real-time, unread-counted notifications when another user reacts to a post, comment, or post photo, and when another user shares their post. Notification rows show the actor’s name, the correct target, and the selected reaction glyph.

Mia likes your post Mia reacted 😂 to your post Mia reacted ❤️ to your comment Mia shared your post

Done when: the recipient sees a single current reaction alert per reactor and target; changing that reaction updates its glyph instead of adding a duplicate; removing it removes the alert; all activity types affect the navbar/page unread count and refresh live; and a share creates a notification linked to the original post.

Locked product decisions: cover posts, comments, post photos, and shares. Never notify the actor about their own action. A reaction has one notification per recipient + actor + target: an emoji change updates it while preserving its read state; reaction removal deletes it. Every successful share is a separate, persistent event and creates one notification. No push, email, sound, batching, or notification preferences in this plan.

Context and closest analogs

  • src/services/ReactionService.ts owns post, comment, and photo reaction writes. It already reads the target before writing, so it is the correct place to identify the recipient and request notification changes.
  • src/services/PostService.ts#share validates and creates a share wrapper; it is the correct place to notify the original post’s author after a successful share.
  • NotificationService.notify, NotificationModel, and NotificationRealtime are the existing service → model → socket flow. Comments and friend requests are the closest existing notification analogs.
  • frontend/src/pages/NotificationsPage.tsx contains the notification type map and row renderer. ReactionIcon.tsx and reactionOptions.ts already render the exact six supported glyphs.
  • notifications.type is a string. It currently has post/comment/photo target columns but no reaction emoji and no uniqueness guard for a single reaction alert.

  • Add nullable reaction_emoji to notifications, constrained to the existing reaction enum values where the database supports it.
  • Add partial unique indexes for each reaction target type over recipient, actor, type, and its concrete target ID. This gives the model a database-enforced upsert key and prevents duplicate alerts under concurrent requests.
  • The notification API adds reactionEmoji: ReactionEmoji | null to each view. Existing notification response fields and routes stay compatible.
  • Notifications created before this feature remain readable; their new field is null and their current visual treatment stays unchanged.

Constraints

Must

  • Follow routes → controllers → services → models; no new direct DB access in a service.
  • Use the existing six reaction choices and ReactionIcon; no duplicated glyph mapping.
  • Keep notification reads stable: an emoji update must not re-mark a read alert as unread.
  • Publish a socket count update for create, update, and delete so an open Notifications page refreshes.
  • Preserve current comment, friend-request, reaction-summary, share, and navigation behavior.

Must not

  • No new routes, npm dependencies, notification settings, push/email delivery, sounds, or aggregation.
  • No notification on reaction removal after its matching alert has been deleted.
  • No notification for self-reactions or self-shares.
  • No broad rewrite of the Notifications page or reaction UI.

Out of scope

  • Reaction notifications for messages.
  • “Mark all read,” pagination, grouping (“3 people reacted”), or actor-block/mute rules.
  • Backfilling notifications for historical reactions and shares.

Risk and pushback

Level 2 — Concern. This touches user-visible activity, counts, and live refresh. The principal failure mode is stale or duplicated alerts, especially because a reaction is an upsert while a share is a new post.

HazardBlast radiusMitigation

Required pushback: do not model this as one generic, unconstrained notification row. Without a durable reaction uniqueness key and matching delete path, concurrent upserts and toggles will make the activity feed untrustworthy.
