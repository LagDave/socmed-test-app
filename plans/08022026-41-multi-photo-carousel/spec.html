Why

Posts today accept at most one optional photo (posts.image_url). Users want Facebook-style albums in the feed — pick several photos when composing, control their order, and browse them horizontally in the card. Plan 08 explicitly excluded multi-image galleries; this plan supersedes that constraint for feed posts only.

What

  • Select up to 10 images from the device when creating a standard feed post via FeedComposer.
  • Order before posting — horizontal thumbnail strip in the composer with move-left / move-right (and remove) per image.
  • Carousel on the feed — images render as full-width cards in a horizontal scroll-snap track; swipe on touch, drag-scroll on desktop; dot indicator for position when count > 1.
  • Backward compatible — existing single-image posts keep working; API continues to expose imageUrl (first/cover) plus new imageUrls: string[].
  • Share embeds — reshared originals with multiple images show the same carousel inside SharedPostEmbed.

Constraints

Must

  • Allow 1–10 images on standard feed posts created via FeedComposer
  • Persist explicit order (sort_order 0…n−1)
  • Composer shows horizontal thumbnail strip with reorder + remove before submit
  • Feed, post detail, profile timeline, and share embed use the same carousel when imageUrls.length > 1
  • Carousel: horizontal scroll-snap, dot indicators, overscroll-behavior-x: contain — no arrow buttons (4A)
  • Single-image posts render as today (no carousel chrome for n=1)
  • Image-only posts allowed — composer may post with images and empty caption (body: " ")
  • Upload-all-then-create: any upload failure aborts; no partial post
  • Validate every URL with /^\/uploads\/[A-Za-z0-9._-]+$/ on create
  • Set posts.image_url to first image on create (cover mirror)
  • Backfill migration for existing posts with image_url
  • SharedPostEmbed shows carousel (or equivalent) for multi-image originals
  • Preserve text-only posts, reactions, comments, share behavior

Must Not

  • No new npm carousel / DnD dependencies
  • No batch upload endpoint in v1 (reuse single-file upload)
  • No multi-image comments, DMs, or profile-activity posts
  • No video
  • No page/CMS publishing tool in this plan
  • No breaking removal of imageUrl from API (keep for compat)
  • No client-side-only ordering (order must persist server-side)
  • No carousel prev/next arrow buttons on post cards (4A)
  • No post-publish image edit in v1 (10B — follow-up plan)

Out Of Scope

  • Facebook Pages / separate page publishing UI
  • Editing image order or attachments on an already-published post — follow-up plan (10B)
  • Lightbox / fullscreen gallery with zoom
  • Automatic image compression or CDN
  • Orphan upload cleanup job (note as follow-up if partial failure occurs)
  • Album titles separate from post body

Risk

Level 2 — Concern. Schema addition touches every post read path; partial upload failure can orphan disk files; carousel UX must not break scroll on mobile feed.

Data & API

Migration

  • Create post_images (see migrations/README.md).
  • Backfill one row per existing non-null posts.image_url.
  • Idempotent guards (hasTable / hasColumn style).

PostView (BE + FE)

  • Add imageUrls: string[] — ordered, may be empty.
  • Keep imageUrl: string | null — equals imageUrls[0] ?? null when hydrated.

Create post

  • POST /api/posts body extends to accept imageUrls?: string[] (max 10).
  • If imageUrls provided, ignore standalone imageUrl or treat as alias for single-element array — pick one rule at execute (recommended: prefer imageUrls when non-empty).
  • Insert post_images rows in order; set posts.image_url to first URL or null.
  • Post still requires body min 1 OR at least one image (existing image-only posts use body " " — preserve that).

Read paths

Feed, get-by-id, profile posts list, share hydrate — all return imageUrls populated from join/batch query.
