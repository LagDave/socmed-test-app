Why

The Messages title, description, unread badge, and actions currently sit on the page background above a separately rounded inbox card. The supplied screenshot makes the visual break clear: the card does not feel connected to the header that introduces it.

What

Render the existing Messages header inside the existing inbox card, creating one continuous Messages surface. Keep the header content and all interactions unchanged, without a horizontal divider before the compose panel or conversation list. At every viewport width, make this inbox surface full-bleed beneath the app navbar, without rounded outer corners or shadow. At desktop width, show the selected conversation in a left detail pane and the inbox as a fixed right pane; at mobile width, retain the current one-screen-at-a-time route flow.

Done when: on /messages, the title/description and header actions are visibly enclosed by the same outer surface as the inbox content, without a gap or duplicate card treatment; desktop renders a responsive 22rem–53.5rem inbox sidebar plus an empty/selected detail pane; mobile renders only the active route surface; and all inbox states and controls work exactly as before.

Context and closest patterns

  • frontend/src/components/messages/InboxView.tsx owns both the page header and the feed-card overflow-hidden shadow-sm body. It is the sole application file this change should touch.
  • frontend/src/index.css defines the shared .feed-card surface. Reuse that established style rather than introducing a new card abstraction or global selector.
  • frontend/src/components/messages/ThreadViewContent.tsx is the closest Messages analog: its header and body share one continuous feed-card container.

Scope and decisions

Must

  • Move the current InboxView page-header block into the existing feed-card overflow-hidden shadow-sm container.
  • Use the existing spacing without adding a horizontal rule between the header and the compose/conversation content.
  • At every width, break this inbox out of the shared centered column, remove the card’s outer rounding/shadow, and fill the viewport below the navbar.
  • At lg and above, render the existing inbox and selected thread as a two-pane layout; do not change the conversation URL format.
  • Below lg, show only the inbox at /messages or only the selected thread at /messages/:conversationId.
  • Preserve the exact title, description, unread count, New message, display-mode, and Message settings controls.
  • Keep empty, loading, error, populated, and open friend-picker states contained by the same card.

Must not

  • No changes to message routes, API calls, socket refreshes, conversations, unread calculation, or friend-picker behavior.
  • No change to thread data fetching, message actions, thread header controls, or Message settings.
  • No new component, dependency, card system, or global theme/layout refactor.

Out of scope: changing inbox row styling, message data, API contracts, desktop conversation selection defaults, Message settings, or a new responsive-state library.

Required pushback — Level 3: a desktop split pane touches the route composition and both existing view containers. Duplicating inbox or thread instances for breakpoints would multiply sockets, polling, and UI state. The plan instead mounts one inbox and one selected thread, applies CSS-only visibility below lg, and preserves the existing route as the source of the selected conversation.
