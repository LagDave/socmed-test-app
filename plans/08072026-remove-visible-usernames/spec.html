Why

Identity is visually duplicated throughout the product: people see a display name followed by @username in feeds, sharing, messaging, friends, profile, navigation, and reaction surfaces. The requested UI should use display names only, without treating usernames as removable domain data.

What / locked behavior

  • Remove every currently rendered @username text node from product UI: post and comment cards, shared-post preview/embed, share dialog, reactions, friends, inbox, live thread header, legacy thread-header component, profile header, and navbar profile menu.
  • Keep display names, avatar/profile links, click targets, and existing truncation/flex containers. Removal must not leave empty secondary lines or hidden placeholder spacing at desktop or mobile widths.
  • Keep every username-bearing API/type/authentication/route/lookup consumer intact. In particular, /u/:username links, profile fetch/redirect/copy-link behavior, friend requests, friend and message search matching, and username-based conversation opening remain unchanged.
  • Accessibility remains meaningful through existing display-name labels (for example, “{display name}'s profile”). No new username announcement is required where the adjacent display name already identifies the target.
  • The plan’s visual removal includes discovered instances outside the initial examples: comment author, reaction participant, profile header, and navbar menu. Username entry/edit fields are not @username presentation and remain in scope only as protected consumers, not edit targets.

Constraints

Must

  • Read each target immediately before modifying it and re-confirm its profile/link/API consumers.
  • Preserve display names, responsive containers, focus behavior, and meaningful accessible labels.
  • Search the complete frontend source for remaining rendered @username text before handoff.
  • Run type-check, build, lint, and applicable convention checks; update this spec’s revision log if scope changes.

Must not

  • Do not remove or rename username fields from types, payloads, URLs, auth, backend, or database code.
  • Do not alter profile route formats, username lookup/search, friend request lookup, or message-opening API contracts.
  • Do not add a dependency, change layout systems, or perform unrelated cleanup/refactoring.

Out of scope

  • Changing username creation, editing, validation, uniqueness, or account settings.
  • Changing how usernames appear in URLs, browser address bars, copied profile links, API responses, developer tools, or screen-reader-only content where a future accessibility need is explicitly established.
  • Redesigning identity, name disambiguation, search ranking, or profile permissions.

Risk & required pushback

Level 2 — Concern. The same username property drives presentation and identity routing. A broad “remove usernames” edit would break profile navigation, messaging, lookup, or authentication. The requested visual scope is safe only if every removal is a render-only deletion and all non-render consumers are preserved.

Resolved boundary: Profile header and navbar menu are included because they are discovered visible @username instances. Username inputs, “Add by username” guidance, and profile URLs are intentionally retained because they are lookup or account-management affordances, not handle presentation.
