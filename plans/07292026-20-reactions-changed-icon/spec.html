Why

Plan 15 shipped Facebook-style reactions using Unicode emoji glyphs (👍 ❤️ 😂 😮). The rest of the chrome (theme, nav, comment/reply) already uses lucide icons. Users want the same four reactions and behavior, rendered as icons instead of emoji so the UI feels consistent.

What

  • Render the fixed set — like, heart, haha, wow — through one shared ReactionIcon component instead of per-surface glyph literals.
  • Locked sticker map (Facebook-equivalent Unicode emoji — FB proprietary art cannot be copied):
    KeyStickerLabel
    like👍Like
    heart❤️Heart
    haha😂Haha
    wow😮Wow
  • Surfaces: ReactionBar (Feed, post detail, comments/replies) and message reactions on MessagesPage.
  • Selected state: ring/highlight on the picker’s active option (stickers are full-color, so there is no fill/tint treatment).
  • Keep hover labels (Like / Heart / Haha / Wow), expand/hold picker UX, pop/wiggle animations, set/switch/clear API behavior, and counts for types with ≥1.
  • API/DB enum keys and payloads unchanged — presentation-only swap.

Done when: no surface renders its own reaction glyph literals — every one goes through ReactionIcon and the locked map above; a ring marks the viewer’s reaction; set/switch/clear + counts still work on posts, comments, replies, and messages; typecheck/build green; acceptance checklist runnable.

Context

  • frontend/src/components/ReactionBar.tsx — EMOJI_OPTIONS with glyph strings; trigger, picker options, and count chips all render those glyphs. CSS classes reaction-emoji-btn / reaction-emoji-pop in index.css.
  • frontend/src/pages/MessagesPage.tsx — local EMOJI_OPTIONS + MessageReactions also render glyphs for picker buttons and count text.
  • Icons already via lucide-react (ThemeToggle, PostActionRow, AppShell). Pattern: h-4 w-4 (md) / slightly smaller for sm; aria-label on controls.
  • Backend reaction keys stay like | heart | haha | wow — do not rename types or routes.

Closest analogs: Plan 18 icon buttons beside reactions; ThemeToggle for compact lucide controls.

Before -x, reset that branch onto kylie/comment-action-icons (13ab6d3 or newer tip) so there is reaction UI to convert. Planning artifacts stay on plan/07292026-20-reactions-changed-icon.

Constraints

Must

  • Same four reaction keys; same set/switch/clear semantics
  • Sticker map locked above (Unicode 👍❤️😂😮); no new dependencies
  • One shared source of truth: lib/reactionOptions.ts owns the map, ReactionIcon renders it
  • Stickers on ReactionBar trigger, expanded picker, and per-emoji counts
  • Stickers on Messages reaction buttons and visible count summary
  • Viewer’s active reaction is marked by a ring on the picker option — not by a fill or tint
  • Keep existing labels, a11y (aria-label / listbox roles), hover expand + touch hold, pop animation
  • Frontend only — no schema, routes, or API contract changes
  • Follow Code Constitution; no business logic moved into UI

Must Not

  • No adding/removing reaction types
  • No new icon packs, image/SVG sticker assets, or copies of proprietary Facebook art — Unicode text glyphs only
  • No per-type color classes or filled/muted icon variants
  • No glyph literals outside lib/reactionOptions.ts
  • No renaming ReactionEmoji / DB enum / request body field emoji
  • No redesign of PostActionRow / comment-icon layout from Plan 18
  • No backend / migration changes

Out Of Scope

  • Who-reacted lists, custom SVG faces for “wow”
  • Navbar / shell work (Plan 19)
Decisions locked: Facebook-equivalent Unicode stickers 👍 / ❤️ / 😂 / 😮 on ReactionBar + Messages · same set/switch/clear behavior · frontend-only · settled visual (no further glyph/icon experiments unless a new continue).

Risk

Level 2 — Concern. Icons are less “emoji-native” than glyphs (especially SmilePlus for wow). Fill treatment must stay readable in light and dark themes. Dual glyph maps (ReactionBar + Messages) can drift if not updated together.
