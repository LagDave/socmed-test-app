Notification sound settings and unread activity

Plan folder: plans/08062026-activity-sound-settings-relocation · Branch: kylie/activity-sound-settings → dev · Risk: Level 2

Why and what

Message settings contained both direct-message and activity sound preferences, even though activity events belong to Notifications. Move activity controls to a notification-settings route and make each domain independently enabled.

Message sounds remain at /messages/settings. Activity sounds move to /notifications/settings, linked from the Notifications header. Existing shared sound preference remains the fallback for both new toggles, preserving current behavior until a user changes either setting.

Activity notifications remain unread when the Notifications page opens. Opening an individual destination or selecting Mark as read changes only that item's recipient-scoped read state. Pending friend requests remain actionable and counted until confirmed or declined.

Refine this behavior to mirror messages: opening an individual comment or reply notification marks only that item read. A friend request gets its own visible Mark as read control, using the existing notification row without accepting or declining it.

When a comment or reply is opened from Notifications, its existing back arrow must return to /notifications. Direct visits to a post or photo thread keep their existing Back to feed or Back to post behavior.

Context, constraints, and risk

  • frontend/src/lib/notificationSounds.ts owns persisted preferences and live audio gating.
  • frontend/src/pages/MessageSettingsPage.tsx and frontend/src/pages/NotificationsPage.tsx own the two user-facing domains.
  • src/models/NotificationModel.ts, src/services/NotificationService.ts, and the notifications route/controller own comment and reply read state.
  • src/models/FriendshipModel.ts and src/services/FriendshipService.ts determine whether a friend-request notification remains visible and pending.
  • frontend/src/pages/NotificationsPage.tsx originates notification navigation; PostDetailPage.tsx and PostPhotoCommentsPage.tsx render the destination back links.
  • No migration, dependency, or notification-event changes. The authenticated notification read route is refined from bulk to item-level POST /api/notifications/:id/read.
  • Risk Level 2: an incorrect preference migration could unexpectedly mute audio. Mitigation: read the legacy shared flag as the fallback for both new domain flags.
  • Risk Level 2: a read action could leave the badge stale. Mitigation: refresh the list and count only after the existing endpoint succeeds.
  • Risk Level 2: treating a friend request as read must not accept, decline, or hide it. Mitigation: retain the existing notification row's is_read state, while filtering visibility by the pending friendship.
