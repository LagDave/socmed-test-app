Why

Post detail shows a flat comment list. Users need a Reply control on each top-level comment and indented replies under that parent, with the reply box appearing next to that comment so long threads stay easy to answer.

What

  • Reply button on the right of each top-level comment row (ghost sm, aligned with author/body row).
  • Clicking Reply opens an inline composer under that parent (“Replying to {displayName}” + Cancel + textarea); it scrolls into view. Submit includes parentId.
  • Bottom “Write a comment” form remains for top-level comments only (not used for replies).
  • After send, list shows parents chronological; each parent’s replies indented beneath it, also chronological.

Done when: Reply appears right-aligned on parents; reply composer is inline under the parent (no modal); replies indent under parent; API rejects a parentId that is not a top-level comment on the same post; typecheck/build green.

Context

UI today: frontend/src/pages/PostDetailPage.tsx — flat <ul> + bottom form. No comment components yet; keep logic on this page unless a tiny presentational row extract helps clarity.

API today: GET/POST /api/posts/:postId/comments, create body { body, imageUrl? }. Model/service/types lack parent.

Closest analog: ghost size="sm" buttons in AppShell / FriendsPage for Reply; ThemeToggle pattern for compact controls.

Prior plan: 07272026-06-socmed-comments shipped linear comments. This plan adds one nesting level via nullable parent_id.

Constraints

Must

  • Add nullable parent_id FK → comments.id (ON DELETE CASCADE or SET NULL — prefer CASCADE so deleting a parent removes its replies)
  • Create accepts optional parentId; when set, parent must exist, belong to same post_id, and itself have parent_id IS NULL
  • CommentView exposes parentId: string | null
  • List response may stay flat; SPA groups for display (parents asc, replies under parent asc); orphan replies (missing parent) still render
  • Reply control only on top-level comments; reply composer is inline under that parent
  • Auth unchanged (requireAuth)

Must Not

  • Modal / overlay reply composer
  • New npm dependencies
  • Notifications / @mentions / edit
  • Change delete ownership rules (owner-only); cascade is DB-level

Out Of Scope

  • Deep / recursive threads beyond one parent → children level
  • Collapsing threads, reply counts, sort toggles
  • Realtime / websockets
Decisions locked: one nesting level; inline reply composer under the parent (scrolls into view); bottom form for top-level comments only; parents then indented children, both chronological.

Risk

Level 2 — Concern. Schema + create contract change; plan 06 assumed linear-only.
