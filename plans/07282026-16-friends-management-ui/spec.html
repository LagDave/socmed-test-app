Why

The Friends page works functionally but reads as a bare scaffold: flat sections, button label “Request”, and empty states that say “None”. Users managing requests and mutuals need a clearer dashboard composition — header hierarchy, a polished request row, structured sections, and professional empty states — without fracturing the app’s black-and-white design system.

What

A visual redesign of the existing Friends management surface on /friends: page-scoped soft canvas, centered white container card, clearer header + request form, stacked Incoming / Outgoing / Mutuals sections with dividers, and icon + microcopy empty states. Behavior and API contracts stay unchanged.

Done when:

  • Friends page shows a centered card on a soft page-local canvas (not a global body override)
  • Heading is “Friends”; subtitle is “Requests and mutuals.”
  • Request row has a taller Username input and a “Send Request” primary button with hover affordance
  • Incoming, Outgoing, and Mutual Friends are stacked sections with clear horizontal dividers
  • Each empty section shows a muted user silhouette icon + professional microcopy (not “None”)
  • Existing accept / decline / cancel / send-request flows still work
  • Light and dark themes both look intentional on this page
  • Frontend typecheck and build pass

Context

Page today — frontend/src/pages/FriendsPage.tsx loads /api/friends/inbox + /api/friends/mutuals, posts requests, accept/decline/cancel. Structure is three plain <div> lists with None / None yet empty text. Button label is “Request”.

Shell — AppShell wraps pages in main.mx-auto.max-w-3xl. Friends redesign stays inside that width; page may use a full-bleed-within-main soft canvas + inner card.

UI kit — Reuse Button and Input from @/components/ui/*. Icons via installed lucide-react (already used by ThemeToggle).

Tokens — frontend/src/index.css B&W light/dark variables. Prefer utility classes bound to tokens over new hex literals. If a page-scoped canvas needs a dedicated class, add a small Friends-only block in index.css that reads existing CSS variables (light + .dark).

Closest analog — Current FriendsPage itself; no separate dashboard component exists. Do not invent a parallel friends API client.

Execution branch — Implement on kylie/ui-beautification (planning artifacts authored on plan/07282026-16-friends-management-ui worktree).

Constraints

Must

  • Preserve all existing friend API behaviors and error handling
  • Keep B&W design tokens — no Meta blue / new brand accent
  • Scope background/canvas styling to the Friends route only
  • Support light and dark themes
  • Use stacked sections (Incoming Requests, Outgoing Requests, Mutual Friends)
  • Empty states: muted icon + microcopy per section
  • Rename submit CTA to “Send Request”
  • Follow Code Constitution frontend layering (presentation in page/components; API via existing client)

Must Not

  • No backend, route, migration, or API contract changes
  • No new npm dependencies
  • No global body background rewrite
  • No Tabs implementation (deferred)
  • No drive-by restyles of Feed / Profile / Auth pages
  • No change to friendship business rules

Out Of Scope

  • Avatars / profile photos on list rows
  • Search/filter of mutuals (Username field remains “send request”, not list filter)
  • Pagination, infinite scroll, or realtime updates
  • Unfriend action on mutuals (unless already present — it is not today)
  • Global design-system token overhaul

Risk

Level 2 — Concern. Main hazard is visual inconsistency if Friends becomes a one-off “Facebook island” while the rest of the app stays B&W. Mitigated by locked decision B (tokens only).

Consumers touched: FriendsPage (primary), optionally index.css for page-scoped helpers. No backend consumers. AppShell unchanged unless a tiny layout tweak is required for the card (prefer page-local).
