Why

The recently added Messages-only light/dark mode creates a second appearance preference, stored separately from the application preference, and adds the Moon/Sun button shown in the inbox header. The approved outcome is to remove that feature completely so Messages follows the established global appearance again.

What

Remove the independent Messages theme provider, context, persistent socmed-messages-theme preference, inbox Moon/Sun control, scoped CSS token overrides, and conversation-theme darkening variant. Keep the global profile/menu appearance control, the New message action, Message settings action, and the per-conversation Customize chat theme palette unchanged.

Done when: /messages contains only its New message and Message settings header actions; Messages always reflects the global theme; a saved conversation palette remains selectable and readable; and frontend quality gates pass.

Constraints and decisions

Must

  • Use the existing global ThemeProvider as the sole appearance authority.
  • Remove every production import/reference to the feature-only context, provider, and toggle.
  • Preserve message data, APIs, sockets, search, composition, and conversation-theme persistence.
  • Record a new changelog release entry describing the removal.

Must not / out of scope

  • Do not add a replacement Messages-local setting or mutate the global theme implementation.
  • Do not remove the Palette / Customize chat theme control or its API.
  • Do not add dependencies, database migrations, or an automated test framework.
  • Do not erase the historical 0.1.39 changelog entry.

The obsolete browser key socmed-messages-theme is intentionally left unread rather than adding one-time cleanup code. Once the provider is gone it cannot affect the UI, and a cleanup effect would reintroduce the removed feature boundary.

Risk and mitigation

Level 3 — structural risk: this branch was originally created from local dev at b904728, which predates the feature. The feature exists on current origin/dev at 72d7860. Executing without first moving the branch to that baseline would produce no actual removal and risk overwriting newer integration work. Mitigation: require a clean worktree and rebase kylie/remove-message-switch-mode onto origin/dev before modifying code.
