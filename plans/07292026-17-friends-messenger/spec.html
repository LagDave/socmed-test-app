Why

SocMed already has mutual friendships and a friends management surface, but friends still cannot talk privately. A 1:1 messenger — inbox, thread, text, images, reactions, unsend — makes the social graph useful beyond the feed without inventing groups or a realtime infrastructure stack in the same plan.

What

A friends-only 1:1 messenger with a dedicated Messages surface, REST APIs, and short polling while a thread is open.

Deliverables:

  • Schema — conversations (ordered user pair), messages (text and/or image, soft-unsend), message_reactions, per-user last-read on the conversation
  • API — list/create conversation, list/send messages, unsend own message, react/unreact, mark read, unread count
  • SPA — /messages inbox + /messages/:conversationId thread; AppShell Messages nav icon with unread badge; icon entry points on Friends mutual rows and friend profiles
  • Delivery model — request/response + short polling in an open thread; unread badge refresh on navigation and while Messages routes are active

Done when:

  • Two accepted mutuals can open a conversation and exchange text and images
  • Non-friends cannot create or send into a conversation (403/deny)
  • Own message unsend leaves a visible “Unsent a message” placeholder for both sides
  • Either participant can add/change/remove a reaction from a fixed emoji set on a non-unsent message
  • Messages nav shows an unread badge; Notifications bell/feed is unchanged (no message rows there)
  • With a thread open, new messages from the peer appear without a full page reload (via poll)
  • Frontend typecheck/build and backend typecheck pass; acceptance checklist passes or waived in writing

Locked Decisions

3 Content Text + images + reactions Reuse POST /api/uploads for images. Message reactions are a new table (not dependent on post-reactions PRs). Fixed emoji allow-list.
4 Chat chrome Unread badge yes · Unsend → “Unsent a message” · no edit / read receipts / typing Unsend is soft tombstone, not hard delete. Typing/receipts need stronger realtime semantics — defer.
5 Entry points A — Messages nav + icon on friend surfaces AppShell icon between Friends and Profile. Friends mutual row + other-user profile get a message icon (not the word “Message”), only when accepted mutual.
6 Friendship edge A — gate on accepted; no unfriend in this plan Send/create requires accepted friendship. Unfriend API stays out of scope; when it exists later, threads become read-only.
7 Notifications B — Messages badge only Do not add a message type to the Notifications bell feed. Unread lives on the Messages nav badge (+ inbox UI).
8 Sizing A — single plan Schema, API, and SPA ship together for spec-code parity.
Placement: first-class /messages surface in AppShell — not buried inside Friends. Friends/Profile icons are shortcuts into get-or-create conversation.

Context

Gate — FriendshipModel.findPair + status === "accepted", or add areFriends(a,b) helper used by MessageService only (do not invent a second social graph).

Auth — cookie session + requireAuth on all message routes (same as friends/posts).

Uploads — existing POST /api/uploads returns /uploads/… URL; message create accepts that URL after validation (must be same-origin upload path pattern already used by posts/avatars).

Closest analogs — Comments (ordered text create + author hydrate + ownership delete) for messaging; Friends mutuals list for recipient picker / icon row; AppShell notification badge for unread badge UX (separate count endpoint).

Shell — frontend/src/components/AppShell.tsx NavIcon pattern; add Messages with Lucide MessageCircle (or equivalent already available).

UI language — B&W tokens, soft-page canvas optional on Messages routes to match Friends/Notifications; no new brand accent.

Layering — routes → controller → service → model; Zod in service; ok/fail/AppError; frontend via api client only. Follow Code Constitution.

Execution note — Implement on a feature branch cut from current dev (or agreed integration tip), not on the planning worktree. Planning artifacts live under this folder.

Data Model (sketch)

TablePurpose
conversations id, user_a, user_b (canonical user_a < user_b), unique pair, created_at, last_message_at, user_a_last_read_at, user_b_last_read_at
messages id, conversation_id, sender_id, nullable body, nullable image_url, unsent_at nullable, created_at. At least one of body/image required on create. Unsent clears body/image for clients and sets unsent_at.
message_reactions message_id, user_id, emoji, unique (message_id, user_id) — one reaction per user per message (replace on change). Cascade on message delete only if hard-deleted (prefer keep rows; hide when message unsent).

API Surface (intended)

MethodPathBehavior
GET/api/messages/conversationsInbox: peer preview, last message snippet, unread flag/count, sorted by last_message_at
POST/api/messages/conversationsBody { username } or { userId } — get-or-create 1:1 if accepted mutual; else deny
GET/api/messages/conversations/:idThread messages (cursor/limit), include reactions summary; participant-only
POST/api/messages/conversations/:id/messagesSend text and/or imageUrl; requires still-accepted friendship
DELETE/api/messages/messages/:idUnsend own message → tombstone “Unsent a message”
PUT/api/messages/messages/:id/reactionSet/replace emoji from allow-list
DELETE/api/messages/messages/:id/reactionClear own reaction
POST/api/messages/conversations/:id/readBump current user’s last-read timestamp
GET/api/messages/unread-count{ unread: number } for AppShell badge (conversations with activity after last-read)

Exact path names may match repo pluralization style; keep under /api/messages and document any rename in the Revision Log.

Constraints

Must

  • Accepted mutual required to create conversation and to send
  • Participant-only access to conversations/messages
  • Unsend = soft tombstone visible as “Unsent a message”
  • Images via existing upload pipeline (no parallel uploader)
  • Fixed emoji allow-list for reactions (document set in service constant)
  • Messages unread badge separate from Notifications counts
  • B&W tokens; light + dark readable
  • Constitution layering; no business rules in React components

Must Not

  • No WebSockets / SSE / Socket.IO in this plan
  • No group chats / named rooms
  • No message rows in Notifications feed
  • No typing indicators, read receipts, or edit-message
  • No unfriend/block implementation in this plan
  • No new npm dependencies without written justification in Revision Log

Out Of Scope

  • Voice/video, stickers packs, GIF search, link previews
  • Push notifications / email / mobile apps
  • Message search, pinning, forwarding, disappearing messages
  • Presence / online dots
  • Encrypting message bodies at rest beyond normal DB access control

Risk

Level 2 — Concern. Greenfield messaging domain with authz bugs as the main hazard. Realtime (WS) was rejected for this plan to avoid Level 3 infra blast.

Orphan / duplicate 1:1 conversations Inbox chaos Canonical ordered pair + unique constraint; get-or-create in a transaction
Polling load API noise Poll only while thread mounted; backoff when tab hidden; modest page size
Unsend vs reactions Confusing UI Unsent messages show placeholder only; reactions UI disabled/hidden on unsent
Nav density on mobile Header crowding Icon-only NavIcon (same as Friends/Bell); no text label
Migration ID collision with stacked PRs Migrate failures Verify unused timestamp before landing; never steal another PR’s version
Required pushback: Do not expand this plan into WebSockets or group chat mid-execution. If product insists on instant delivery, open a follow-up plan rather than silently widening scope.
