Why

The current Friends page turns an ordinary low-content state into a focal point: a padded outer canvas, an additional large card shadow, and a 64px icon with generous vertical padding create a dramatic visual weight. The supplied screenshot makes the mismatch clear—there is much more decoration and empty panel than content.

What

Give /friends a single quiet, message-style container around its working area. Match the Messages inbox’s feed-card surface and restrained shadow-sm, while keeping the request form borderless inside it, the compact status rows, and the simplified header. Do not restore the former nested canvas or custom heavy shadow.

Before: page → padded outer canvas → heavily shadowed dashboard card → tall empty state After: page → one Messages-style card → inline request form → divided sections → compact status row

Context and closest analog

  • frontend/src/pages/FriendsPage.tsx owns the /friends route, dashboard composition, errors, search, message navigation, and unfriend dialog.
  • frontend/src/components/FriendsEmptyState.tsx owns the empty-state icon, copy, action slot, and dashboard loading shell.
  • frontend/src/index.css contains Friends-scoped canvas, dashboard, section, row, and search styles; shared .feed-card is used by Feed, Messages, and Profile.
  • frontend/src/components/FriendsRequestForm.tsx and FriendListRow.tsx are existing Friends-only patterns that must remain behaviorally unchanged.

Closest visual analog: the existing page-level section hierarchy, using Friends-only dividers rather than a shared card token. No shared card token should change.

Constraints

Must

  • Preserve incoming/outgoing request mutations and error presentation.
  • Preserve mutual search, Escape/focus behavior, message navigation, unfriend confirmation, and loading skeleton.
  • Retain light/dark contrast and existing keyboard focus states.
  • Keep empty-state title and supporting copy available to all users.

Must not

  • Do not edit shared .feed-card, global canvas, navigation, or route behavior.
  • Do not add animation, gradients, decorative artwork, dependencies, API calls, or data changes.
  • Do not redesign friend rows, add suggestions, or alter empty-state copy.

Out of scope

  • Friend-row density or action-button redesign.
  • Notifications' friend-request presentation.
  • Server-side friend search, pagination, or realtime updates.

Risk and blast radius

Level 2 — Concern: editing shared card styles would subtly alter Feed, Messages, and Profile. Future-us will hate a visual-only Friends request that changes unrelated cards. Mitigation: remove the card only from the Friends composition and delete or adjust only .friends-* rules. A second risk is losing readable grouping once the card is gone; mitigate with existing section dividers, consistent Friends spacing, and desktop/narrow-width acceptance checks. A third risk is over-compacting the empty state; retain readable copy, centered alignment, and action space.

Known consumers: /friends is the primary route. The request form, rows, empty state, and skeleton are Friends-only; shared .feed-card is not in scope.
