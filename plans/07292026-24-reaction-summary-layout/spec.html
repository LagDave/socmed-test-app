Why

After Plan 18, the action row reads [react trigger] [per-type count chips] [comment]. The count chips sit between the react control and the comment icon, crowding the left and leaving empty space on the right. Users want a Facebook-style split: action controls on the left, reaction presence summarized on the right.

What

  • Action row layout becomes:
[ react trigger ] [ comment / reply ]  …………  [ ❤️ 👍 ]  3
  • Left: reaction trigger (picker UX unchanged) immediately followed by the existing comment icon (posts) or reply icon (parent comments).
  • Right: when total reactions > 0, show a cluster of distinct reaction stickers that have count ≥ 1 (no per-type numbers), then a single total count beside the cluster.
  • Cluster order follows REACTION_OPTIONS (like → heart → haha → wow), skipping zeros. Tight adjacency is required; slight negative-margin overlap is allowed if it stays readable.
  • Surfaces: Feed posts, post-detail posts, parent comments, replies — all via ReactionBar.
  • Hide the right summary entirely when total is 0.
  • Set / switch / clear, hover labels, expand/hold picker, stickers, and API payloads unchanged.

Done when: posts and comments/replies show left controls + right clustered icons with one total; comment/reply icons sit beside the trigger (not after counts); no per-type count chips remain on ReactionBar; typecheck/build green; acceptance checklist runnable.

Grill locked (1A / 2A / 3A / 4A): full-width justify-between · total count (not per-type) · ReactionBar on posts + comments/replies · Messages out of scope.

Context

Today (on kylie/reactions-changed-icon / plan tip ef44831):

  • frontend/src/components/ReactionBar.tsx — root is inline flex; after the trigger it maps visibleCounts as [icon][n] chips per emoji with count > 0.
  • frontend/src/components/PostActionRow.tsx — flex row: {children} (ReactionBar) then comment icon. Not full-width; no right slot.
  • FeedPage / post-level PostDetailPage — PostActionRow wraps ReactionBar.
  • Comment / reply rows on PostDetailPage — ad-hoc flex with ReactionBar then ReplyActionButton (parents) or ReactionBar alone (replies).
  • ReactionSummary already has counts: Record<ReactionEmoji, number> — total is a client sum; no API change.
  • Stickers via ReactionIcon + REACTION_OPTIONS (Plan 20).

Closest analog: Facebook post footer (actions left, reaction stack + total right). Composition fix belongs in ReactionBar + thin updates to PostActionRow / comment flex wrappers — do not fork count logic into pages.

Recommended composition (implementation hint, not a second pattern): give ReactionBar an optional actions?: ReactNode slot rendered immediately after the trigger on the left; make the bar w-full with justify-between; right side = cluster + total. Then PostActionRow passes the comment control as actions (or composes equivalently) instead of placing comment after the entire ReactionBar. Parent comments pass ReplyActionButton the same way.

Constraints

Must

  • Left group: react trigger + comment (posts) or reply (parent comments); replies may have trigger-only left group
  • Right group: clustered stickers for types with count ≥ 1 + single total; hidden when total is 0
  • Row stretches to content width (w-full / justify-between) so the summary sits at the far right of the post/comment card
  • Preserve picker UX, stickers, a11y labels on the trigger, set/switch/clear
  • Summary has accessible text (e.g. aria-label with total and which types)
  • Frontend only — no schema, routes, or payload changes
  • Follow Code Constitution; no business logic in UI beyond summing existing counts

Must Not

  • No per-type numeric chips on ReactionBar
  • No moving comment/reply icons to the right of the summary
  • No Messages / messenger reaction layout changes
  • No new reaction types, deps, or sticker redesign
  • No backend / migration changes
  • No who-reacted popover

Out Of Scope

  • Messages reaction chips (Plan 17 / 20 surfaces stay as-is)
  • Clicking the cluster to list reactors
  • Navbar / shell work

Risk

Level 2 — Concern. Composition change: today comment is a sibling after ReactionBar (which includes counts). Naïvely right-aligning counts inside ReactionBar without relocating comment yields [trigger …… cluster][comment] — wrong. Must recompose so comment/reply stay in the left group.
