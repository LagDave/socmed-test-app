Why

An image-only post with one uploaded photo renders a per-photo Comment action. That action currently opens the photo-specific comment route. Separately, the normal post detail page suppresses the general CommentsSection for photo posts without a caption or existing post-level comment. The supplied screenshot is that empty state: the action is visible, but no input composer is rendered.

The requested interaction is unambiguous: when a post contains exactly one image, its Comment action must open the post’s general comments section, where a signed-in user can immediately type text, attach a photo, or do both.

What

  • Route a single-image post’s Comment action to /posts/:postId#comments, rather than /posts/:postId/photos/:photoId.
  • Always render the general comments section for a single-image post, including when it has no caption and no prior comments; the hash destination scrolls to and focuses its composer.
  • Scroll the actual top-level composer into a useful viewport position—not merely the comments header—whenever general post comments are opened through #comments.
  • Show the post-level general comment count beside that single-image action, because it now points to—and creates—general comments.
  • Keep multi-image albums unchanged: each image retains its own route, scoped thread, and photo comment count.
  • Remove the redundant carousel-only album header (title, helper text, and album-size badge) so the photos begin directly at the carousel surface.

Done when: clicking Comment on a signed-in, single-image post opens its general comment composer; text-only, photo-only, and text-plus-photo submissions appear in the general thread. A multi-image album still opens the selected photo’s own comment thread.

Context and closest analog

  • frontend/src/components/PostMediaGallery.tsx owns each in-detail photo action. PostPhotoSlide currently routes every persisted image to postPhotoCommentsPath and displays image.commentCount.
  • frontend/src/components/PostCard.tsx creates PostMediaActionsConfig for the detail gallery. It already has the post’s general commentCount, which is the correct value to pass to the single-image action.
  • frontend/src/pages/PostDetailPage.tsx decides whether the general CommentsSection mounts. Its current photo-thread guard is the direct reason the screenshot has no composer.
  • frontend/src/components/CommentsSection.tsx renders the top-level composer at the end of the thread. Its existing section ref identifies the card header, not the composer input.
  • PostMediaAlbum in frontend/src/components/PostMediaGallery.tsx renders the screenshot’s header. The image count remains available through the existing per-image position marker; no data or route contract depends on this decorative block.
  • Closest supported flow: text-only posts already route their Comment action to /posts/:postId#comments and mount this same general CommentsSection.
Blast radius: the in-detail action row for all image posts and the post-detail general comments section. Backend comment creation, uploads, comment threading, notification handling, and database schema do not change. The multi-photo route remains the protected compatibility path.

Constraints

Must

  • Use the existing post-detail route, hash scrolling, and CommentsSection; add no dependency.
  • Keep general and photo-specific comment data explicitly separate.
  • Preserve post-image reactions, share controls, and the existing action-row layout.
  • Run frontend typecheck, lint, build, and contained UI acceptance.

Must not

  • No backend, route-server, API-schema, migration, or notification change.
  • No merging or migrating existing photo comments into the post-level thread.
  • No change to album routing or per-photo counters.
  • No unrelated visual refactor.

Out of scope

  • Displaying general comments inside the photo-specific page.
  • Comment/reply design, editing, mentions, and reaction behavior.
  • Changing a post that has no persisted image ID or any profile-activity media behavior.

Risk and mitigation

Level 2 — concern. General and photo comments are intentionally distinct data sets with distinct counters. Redirecting only the link without aligning the counter or mounting the destination composer would leave an inconsistent, apparently broken experience. The change is frontend-only, but both the route semantics and the count must move together.

HazardMitigation
Single-photo action opens a general thread but shows the stale photo countPass the existing post-level count through PostMediaActionsConfig and select it only when total === 1.

Scroll lands on the section title rather than the inputExpose a narrow ref for the existing top-level composer wrapper and scroll that ref with block: "center"; reply composers remain excluded.
Albums lose per-photo threadingBranch exclusively on exactly one resolved image; acceptance covers a two-image album and checks the selected photo ID remains scoped.
