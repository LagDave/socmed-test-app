Reconcile pinned chats with the current dev message architecture

Plan: plans/08042026-44-pinned-chats
Target baseline: origin/dev at 7e1c18b (2026-08-05)
Feature source: kylie/pinned-chats at dd8eee4

This is an integration plan, not permission to merge either branch wholesale. It preserves shared message pins while retaining dev’s split message architecture: route-only MessagesPage, inbox state in InboxView, thread orchestration in ThreadView, and thread rendering in ThreadViewContent.

Why

kylie/pinned-chats forked before the current messages refactor and changes 14 paths also changed on dev. Its old 1,202-line MessagesPage cannot be carried forward: it would overwrite current search, themes, reactions, read state, typing, and the extracted inbox/thread boundaries. A conflict-marker merge is therefore a Level 3 structural risk.

What will be preserved

  • Shared message pins: either participant can pin or unpin a visible, sent message; both participants receive the canonical pinned-message list and a pin/unpin activity event.
  • Pin surfaces: message overflow menu; pinned-messages dialog; timeline activity entries; and the inbox’s latest-pin-activity preview.
  • Current dev behavior: search, theme system logs, reactions, message edit/unsend, delivery/read state, typing, deletion/restore, mobile swipe delete, and realtime updates stay on their existing dev paths.

Deliberate boundary: do not add a thread-header conversation-pin action. The original plan described one, but the shipped source branch does not implement it. Adding it during reconciliation would be new feature work, not preservation.

Risk & required pushback

Level 3 — Structural Risk. Reintroducing the source branch’s old page would erase the architecture and behavior that landed on dev. The only acceptable integration is behavior-by-behavior porting into the current boundaries.

Context & blast radius

  • src/models/ConversationModel.ts is the caller-scoped inbox query. Dev already combines message, reaction, and theme-log activity; reconciliation adds the shared pin-activity projection without dropping any of those inputs.
  • src/services/MessageService.ts is the central participant authorization and response mapper. It must compose current search/theme behavior with pin models and preserve transactions for multi-table pin/unsend/delete work.
  • src/controllers/messages/MessagesController.ts, src/routes/messages.ts, and src/realtime/MessageRealtime.ts own protected endpoints and event contracts.
  • frontend/src/api/messages.ts, frontend/src/api/socket.ts, and frontend/src/api/types.ts are the typed frontend boundary. Follow dev’s api/client.ts convention; no raw HTTP calls or local token reads.
  • frontend/src/components/ConversationListRow.tsx, SwipeableConversationListRow.tsx, and messages/InboxView.tsx remain on dev’s inbox behavior.
  • frontend/src/components/MessageBubbleRow.tsx, messages/ThreadView.tsx, and messages/ThreadViewContent.tsx are the thread seams. The source-only MessageTimeline.tsx and PinnedMessagesDialog.tsx are candidates to add only after their props are adapted to dev’s current timeline.

Applicable Constitution: preserve Routes → Controllers → Services → Models (§7.1–§7.4); use the frontend component → state/effect owner → typed API boundary (§12.1, §14.1–§14.3); ensure server-side participant authorization (§5.4); keep data visibility checks end-to-end (§20.2).
