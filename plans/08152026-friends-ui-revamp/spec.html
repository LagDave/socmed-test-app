Why

The current /friends page is reliable but visually dense: its large unified card, all-caps section labels, and icon-only actions make relationship management feel more administrative than social. The approved direction is a calmer Friends surface: text-first navigation, one quiet search action, split Friends/Requests/Suggested views, and richer row context.

Unlike the prior UI-only Friends upgrade (Plan 37), this plan adds one real capability: friends-of-friends suggestions. It also surfaces presence that already exists in the application rather than inventing an “online” label.

What

Revamp the existing /friends route into a monochrome, token-driven Friends surface. Keep the current page color system—no purple accent, new brand palette, or global theme changes. The route continues to be /friends.

Done when:

  • Current monochrome light/dark tokens remain the visual source of truth; no purple accent or global style changes.
  • Friends, Requests, and Suggested are accessible client-side text-navigation views inside /friends, each with an inline count; switching views does not change a friendship state.
  • A flat Search people action shares that navigation row and reveals a username field only on demand; a search result keeps the existing send-request behavior.
  • Friend rows expose a labeled Message action at desktop widths and a compact accessible treatment on narrow screens; Unfriend stays behind an explicit overflow action and the existing confirmation dialog.
  • Real mutual-friend presence is shown from the established Socket.IO presence system on the Friends view only. Suggested rows do not include isOnline or live presence.
  • Suggested users are second-degree candidates only, exclude self/current accepted friends/pending requests, expose no email, and display their actual mutual-friend count.
  • Profile-link sharing is not implemented.
  • Existing request, search, message, unfriend, loading, error, and reduced-motion behavior survives.

Context and closest patterns

  • frontend/src/pages/FriendsPage.tsx already owns Friends loading, request mutations, mutual search, chat navigation, and unfriend confirmation.
  • frontend/src/components/FriendsRequestForm.tsx, FriendListRow.tsx, and FriendsEmptyState.tsx are Friends-only presentation pieces and are safe to evolve in place.
  • frontend/src/components/FriendPresenceAvatar.tsx already renders a real online indicator using useFriendOnline; FriendPresenceProvider subscribes to presence:friend-update.
  • src/realtime/PresenceRealtime.ts emits authenticated mutual-friend presence updates. It is a consumer to preserve, not a subsystem to rewrite.
  • src/models/FriendshipModel.ts is the correct location for the new graph query. src/services/FriendshipService.ts, FriendsController.ts, and routes/friends.ts establish the route/service/model path.
  • frontend/src/api/messages.ts is the closest frontend domain-API pattern; create a matching api/friends.ts rather than expanding direct HTTP calls in a component.
  • frontend/src/index.css contains the existing Friends-scoped canvas, strip, row, and reduced-motion rules. It must not restyle shared .feed-card behavior; the permanent strip is replaced by the page-scoped revealed search field.

Blast radius: the Friends route, authenticated Friends endpoints, Socket.IO presence display on this route, the friendships query table, and the new safe suggestion DTO. Feed, Messages, Profile, Notifications, AppShell, friendship write semantics, and profile sharing are not changed.

Constraints

Must

  • Preserve authenticated request/accept/decline/cancel/unfriend behavior and response shapes.
  • Follow Routes → Controller → Service → Model and Component → hook → API client boundaries.
  • Use the shared error contract and existing API client; surface errors in the page banner.
  • Respect prefers-reduced-motion, keyboard tab navigation, visible focus, and mobile row constraints.
  • Add index support before shipping a second-degree relationship query.

Must not

  • No hard-coded accent palette or global body/AppShell restyle.
  • No fake presence, static suggestions, random users, or invented shared interests.
  • No email or other unnecessary profile data in the suggestion response.
  • No new dependency, state library, realtime protocol, or database engine.
  • No change to profile-link sharing, blocking, privacy settings, or friendship write rules.

Out of scope

  • Dismiss/block suggested people.
  • Server-side pagination, ML ranking, contacts import, or interest-based recommendations.
  • Presence privacy settings, multi-device analytics, or a new WebSocket event.
  • Friends redesign on Notifications, Messages, Feed, or Profile.

Risk and mitigation

Level 3 — Structural risk. A suggestions endpoint expands discovery from already-related users to second-degree users. The existing generic PublicUser includes email, so reusing it would broaden exposure of PII. The mitigation is locked into this plan: suggestions use a purpose-built, minimal response type and are authenticated, relationship-derived, and query-indexed.

HazardConsumers / impactMitigation
Discovery endpoint leaks email or presenceAuthenticated users outside a direct friendshipReturn only id, display identity, username, avatar URL, and mutualFriendCount; do not call toPublicUser or isUserOnline for this endpoint.
Second-degree query degrades as friendships growFriends page load and databaseUse one set-based model query, limit 6 in the database, and add (status,user_a) and (status,user_b) indexes through a Knex migration.
Suggested row becomes actionable after relationship changesFriends UI stateRefresh suggestions after send/accept/decline/cancel/unfriend; a pending or accepted candidate must disappear.
View switch regresses keyboard/mobile usabilityFriends routeUse aria-pressed toggle buttons with arrow-key navigation and a single-column mobile layout; actions retain names for screen readers.
Shared CSS restyles other pagesFeed, Messages, ProfileOnly introduce .friends-* rules; do not modify shared .feed-card declarations.
Required guardrail: if code review finds the minimal DTO cannot be kept separate from the email-bearing PublicUser type, stop the execution and revise the spec before exposing the endpoint.
