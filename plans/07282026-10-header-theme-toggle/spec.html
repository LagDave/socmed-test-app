Why

The app ships with light-mode-only CSS tokens and a hardcoded light body gradient. Users on kylie/dark-mode need a discoverable way to switch appearance without leaving the header. Placement between Profile and Log out keeps auth actions grouped and matches the explicit request.

What

A persisted light/dark theme system for the SPA, with an icon toggle in the header nav between the Profile link and the Log out button when signed in. Toggling updates all token-driven surfaces immediately and survives reload.

Done when:

  • Signed-in header order is: Feed · Friends · Profile · theme toggle · Log out
  • Clicking the toggle switches light ↔ dark across the app
  • Preference persists in localStorage and restores on reload without a visible flash
  • First visit (no saved preference) follows prefers-color-scheme
  • Frontend typecheck and build pass

Context

Header today — frontend/src/components/AppShell.tsx renders nav buttons inside a flex row. Authenticated block (lines 20–31) is Profile then Log out; this is where the toggle slots in.

Tokens today — frontend/src/index.css defines light-only :root custom properties and a light body gradient. Tailwind v4 maps them via @theme inline. No .dark block exists yet.

Provider pattern — frontend/src/contexts/AuthContext.tsx is the closest analog: create context, hook, provider, wire in App.tsx.

UI kit — Button already supports variant="ghost" and size="icon". lucide-react is installed (Sun / Moon icons).

Recommended mechanism — toggle a dark class on document.documentElement (<html>), with dark token overrides under .dark { … } in index.css. Matches Tailwind dark-mode convention and keeps React/CSS in sync.

Constraints

Must

  • Insert toggle between Profile and Log out in the authenticated nav
  • Reuse existing design tokens — invert the B&W palette for dark mode; no new accent colors
  • Persist theme in localStorage under a named key (e.g. socmed-theme)
  • Apply theme before first paint to avoid flash (inline script in index.html)
  • Follow AuthContext-style provider + hook pattern (ThemeProvider, useTheme)
  • Accessible toggle: aria-label, keyboard operable, icon reflects target mode

Must Not

  • No backend or API changes
  • No new npm dependencies
  • No per-user server-side theme sync
  • No drive-by refactors of unrelated pages

Out Of Scope

  • System-only mode (no explicit “system” tri-state — first visit uses system, then user choice wins)
  • Animating theme transition beyond existing button hover styles
  • Dark-mode variants for uploaded user images / avatars
Logged-out placement (recommended): Show the same toggle before “Sign in” so guests can set theme on login/register pages. User request only specified authenticated placement; this extension is small and avoids trapping guests in light mode.

Risk

Level 2 — Concern. Primary risk is flash-of-wrong-theme (FOUC) on reload if React applies theme too late.

HazardBlast radiusMitigation
FOUC on reload All pages — first paint shows wrong palette Blocking inline script in index.html reads storage + matchMedia, sets dark class before module bundle loads
Hardcoded light body gradient Background stays light in dark mode Add .dark body { … } gradient override in index.css
Token drift Some components look wrong in dark mode Mirror every :root token in .dark; spot-check Feed, Login, Profile

Consumers touched: AppShell, App.tsx, main.tsx (if provider wraps there), index.css, index.html, new ThemeContext + ThemeToggle.
