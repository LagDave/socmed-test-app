Why

The comment composer changes twice on a simple click: focus immediately sets expanded, which changes the shell from a horizontal pill to a column, then the textarea jumps from one to three rows. The supplied screenshot captures that oversized focused state before the user has written enough text to need it.

The intended interaction is calmer: focusing and typing a short comment should retain the original single-row composer. The composer should grow only when the entered content needs more than one visible line.

What

  • Keep both top-level comment and reply composers in their current one-row shell, with compact image-attach and arrow-send affordances, while focused and while text fits on one visual line.
  • Detect actual visual wrapping—not a character-count threshold—then grow the textarea and reveal the existing expanded controls only after a second line is needed.
  • Let the field shrink back to the compact one-row state when text is shortened to one visual line or cleared, unless an attachment is still selected.
  • Keep the reply composer’s “Replying to” banner and cancel context, but give its input the same compact-to-expanded behavior as the top-level composer.
  • Preserve Enter-to-submit, Shift+Enter newline, image attachment, submit/reset, disabled, accessibility-label, light-theme, and dark-theme behavior.

Done when: a short comment can be focused and typed with no focus-triggered size or layout jump; a naturally wrapped or newline-containing comment expands predictably; reducing it returns it to one row; all existing comment and reply submissions still work.

Context and closest analog

  • frontend/src/components/CommentComposer.tsx is the only composer implementation. Its onFocus={() => setExpanded(true)}, conditional rows={expanded ? 3 : 1}, and expanded min-height are the direct cause of the jump.
  • frontend/src/components/CommentsSection.tsx is the only consumer: it mounts a top-level composer and a reply composer. No API, page, backend, or database consumer needs to change.
  • frontend/src/index.css owns .comment-composer-shell and its expanded geometry/transitions.
  • Closest in-app behavior: MessageComposeBar.tsx keeps its textarea at one row; it is a styling reference only, not a shared abstraction candidate.
Blast radius: post-detail and post-photo comment sections, including their inline reply composer. Both composer instances now share the same compact-to-expanded input behavior; reply context and cancellation remain protected.

Locked decisions

Expansion triggerActual textarea visual-line overflow or an explicit newlineViewport width and font metrics determine wrapping; a character threshold would fail across devices.
Focus behaviorFocus alone does not alter either composer layoutThis removes the unwanted first transition shown in both screenshots.
Compact controlsKeep image-attach and icon-only arrow send controls for one-line textTyping a short comment or reply remains directly submittable without opening the expanded footer.

Constraints

Must

  • Use the existing controlled textarea and component state; add no dependency.
  • Use named constants for any line/height cap (§4.2).
  • Keep component concerns local (§13.3); no new global state or API calls.
  • Run frontend typecheck, lint, and production build.

Must not

  • No backend, route, API, schema, migration, or design-system primitive changes.
  • No character-count-only expansion rule.
  • No removal of Enter/Shift+Enter semantics or accessible labels.
  • No change to CommentsSection.tsx unless required solely to preserve a verified composer contract.

Out of scope

  • Comment bubbles, reactions, counts, and visual restyling, except the user-requested separated-media layout for uploaded comment images.
  • Message composer behavior.
  • Comment editing, drafts, mentions, or attachments beyond current behavior.

Risk and mitigation

Level 2 — concern. Measuring wrapped text can oscillate at the one-line boundary if the expanded layout changes the textarea’s available width, and height changes can disrupt mobile or IME input. This is a focused interaction fix, but these failure modes require deliberate verification.

HazardMitigation
Text alternates between one and two lines as controls change widthMeasure against stable textarea geometry; keep the compact width reservation for the send affordance while determining wrapped state. Test at desktop and narrow viewport widths.
Long text expands without a boundUse named one-line and maximum-height values; cap visual growth at the current roughly three-row behavior, then scroll.
Shortened text remains visually expandedRecalculate after each value change and collapse only for the top-level composer with no attachment.
Reply workflow regressesKeep replyingTo as an explicit expanded-mode override; acceptance includes reply/cancel/submit checks.
New frontend convention driftKeep the logic inside the existing component and verify §§13.1, 13.2, 13.3, 17.1, 17.2, and 20.3.
