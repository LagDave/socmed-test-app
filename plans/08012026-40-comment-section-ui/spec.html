Why

Comments shipped in the Jul 31 UI batch with avatar headers and threaded replies, but the section still reads utilitarian: flat text blocks, composer at the top, and a generic "Comments" heading. Feed and Friends surfaces now use elevated cards, pill inputs, and tighter meta rows — comments should match that Facebook-style conversation language without changing API behavior.

What

Target layout (post detail / inline comments):

┌─ comments feed-card ───────────────────────────────────┐
│ (💬)  3 comments                                       │
├──────────────────────────────────────────────────────────┤
│ (●)  ┌─ bubble ─────────────────────┐                    │
│      │ Jane Doe @jane               │                    │
│      │ Great post!                  │                    │
│      └──────────────────────────────┘                    │
│      👍 2  ↩  ·  2h                                      │
│      │ reply rail                                             │
│      (●)  ┌─ reply bubble ───────────┐                     │
│           │ Bob @bob                 │                     │
│           │ Thanks!                  │                     │
│           └──────────────────────────┘                     │
├──────────────────────────────────────────────────────────┤
│ (●)  [ Write a comment ····················· ]  (↑)      │
└──────────────────────────────────────────────────────────┘

Done when:

  • Each comment renders as a rounded bubble card with author name inside (not a separate header row)
  • Meta row below bubble: reactions + reply action + relative timestamp
  • Reply threads show a vertical rail (::before line) indenting nested replies
  • Section header shows icon + count only — no "Comments" heading text
  • Primary composer sits at the bottom of the section (border-top strip), not the top
  • Composer uses pill shell when collapsed; icon-only send when collapsed; expands on focus
  • Inline reply composer appears under the parent thread with reply banner
  • Empty state uses icon + title + supporting copy
  • Light + dark parity via existing B&W tokens; no backend changes
  • Frontend typecheck/build pass; acceptance checklist passes or carries written waivers

Constraints

Must

  • Preserve comment submit, reply, delete, reaction, and photo attach flows
  • Preserve CommentThread grouping and orphan reply handling
  • Frontend-only; presentation in components + CSS per Code Constitution
  • Light + dark theme parity using existing tokens

Must not

  • Backend, schema, or API changes
  • New npm dependencies
  • Global AppShell or feed-card structural changes
  • Drive-by refactors on PostCard, Feed, or Messages

Out of scope

  • Comment sorting or pagination
  • Realtime comment delivery
  • Edit comment
  • Mention autocomplete

Risk

Level 2 — Concern. Primary hazard is composer placement regression (users expect top composer on some surfaces). Secondary: bubble max-width crowding on narrow viewports.

HazardBlast radiusMitigation
Bottom composer breaks scroll-to-comment UX Post detail page Keep sectionRef anchor; composer only moves within section
Reply rail misalignment on deep threads Threaded replies Fixed left margin + ::before rail scoped to .comment-replies-block
Collapsed send button inaccessible Keyboard / screen reader aria-label on icon send; expand on focus
