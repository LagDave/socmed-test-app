Why

Plan 17 shipped a friends-only 1:1 messenger on REST + short polling (thread ~2.5s, Messages unread ~5s while on /messages*). That was an explicit deferral of realtime so the domain could land without inventing infra in the same plan.

Polling works, but peers still wait up to a poll interval, the open thread keeps hammering the API, and the inbox/badge stay dull when the user is elsewhere. Live push is now the follow-up that plan required.

What

Revamp message delivery to Socket.IO push while keeping Plan 17’s REST mutations, schema, authz, and SPA surfaces.

Deliverables:

  • Server — Attach Socket.IO to the existing HTTP server (same PM2 process). Auth handshake via socmed_session cookie. Join each socket to user:{userId}.
  • Emits — After successful REST mutations, fan out: message:new, message:unsent, message:reaction, plus unread/inbox bump events so AppShell badge and inbox can update without polling.
  • SPA — Shared socket client (withCredentials). Thread + badge consume events while connected; restore existing REST poll intervals only while disconnected.
  • Dev/edge — Vite proxy /socket.io → API :3210. Patch SocMed Caddy with an explicit /socket.io* handle if needed (defaults already upgrade WebSockets).

Done when:

  • Two mutuals in separate browsers: send/unsend/react appear on the peer without waiting for the 2.5s poll while sockets are connected
  • AppShell Messages badge updates from events without the 5s poll while connected (including when not on /messages*)
  • Disconnecting the socket re-enables poll fallback; reconnect disables it again
  • Unauthenticated socket handshake is rejected; non-participants never receive another pair’s events
  • No schema migration; REST contracts unchanged
  • Typecheck/build green; acceptance rollup Passed or waived in writing

Event contract (v1)

EventWhenRecipientsPayload (intent)
message:new After MessageService.send Both participants’ user:{id} rooms Message view matching REST send/list shape
message:unsent After unsend Both participants Tombstone message view
message:reaction After set/clear reaction Both participants Updated message view (with reaction summary)
messages:unread (name may be conversation:updated + unread — pick one, document in Rev Log if renamed) After send / markRead (and any mutation that changes unread or inbox peek) Affected user(s) At least { unread }; optionally enough for inbox row refresh (conversation id + last message peek)

Client must ignore events for conversations it cannot access; server must only emit to the two participant user rooms (never broadcast).

Constraints

Must

  • REST remains source of truth for create/read/unsend/react/mark-read
  • Socket.IO on the existing HTTP server; default path /socket.io
  • Auth via socmed_session cookie on handshake; reject if invalid/expired
  • Join user:{userId} on connect; emit only to participant rooms
  • While socket connected: disable thread 2.5s poll and AppShell 5s unread poll
  • While disconnected: restore those polls (same intervals / hidden-tab skip as today)
  • Vite proxy /socket.io → http://127.0.0.1:3210
  • Constitution layering: no business rules in React; no DB in socket handlers beyond session lookup
  • Justify new npm deps in Revision Log

Must Not

  • No schema migrations in this plan
  • No Redis / multi-instance adapter
  • No typing, presence, read receipts, edit-message
  • No group chats / conversation rooms requirement
  • No moving send/read onto socket events
  • No separate WS auth token
  • No folding DMs into Notifications bell
  • No always-on dual poll+WS when connected

Out of scope

  • Push/email notifications, mobile apps
  • Horizontal scale / sticky sessions / Redis adapter
  • Reworking Plan 17 UX beyond delivery wiring
  • Signals app or shared realtime bus with Signals
