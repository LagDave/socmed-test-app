Why

Plan 22 shipped live message delivery over Socket.IO — peers see new messages without polling. The UI still only updates badges and thread content silently. Users who are elsewhere in the app (Feed, Profile, another thread) have no audible cue that a friend messaged them.

Activity notifications (bell: friend requests, comments, replies) remain REST-only with no realtime push. This plan deliberately ships message sounds first because the delivery hook already exists; bell sounds belong in a follow-up plan with socket push.

What

Play a short in-app sound when an inbound DM arrives via message:new, with sensible suppress rules and a user mute toggle.

Deliverables:

  • Sound assets — bundled under frontend/public/sounds/: message.wav (shipped) and activity.wav (bundled for future bell sounds; not wired in v1).
  • Sound module — small frontend helper with a typed SoundKind (message | activity), preload, autoplay-unlock, and play(kind).
  • Global listener — hook mounted from AppShell (or equivalent signed-in shell) on the existing messages socket: play on inbound message:new when rules pass.
  • Suppress rules — no sound for own messages; no sound when the user is already viewing that conversation thread (/messages/:conversationId).
  • Preference toggle — Account Settings → General: “Play notification sounds” (default on), persisted in localStorage only.
  • Autoplay unlock — unlock audio on first user interaction after sign-in (click/keydown), so browsers do not silently block playback.

Done when:

  • Two mutuals: B on Feed hears a sound when A sends a DM; B on the open thread with A does not hear it
  • Own outbound messages never trigger a sound
  • Toggle off → no sounds until toggled back on (survives refresh on same browser)
  • Toggle on → sounds resume after unlock interaction
  • No backend / schema changes
  • Typecheck/build green; acceptance rollup Passed or waived in writing
Grill locked (2026-08-01): Q1=A message sounds only · Q2=A suppress on open thread · Q3=B distinct sound kinds (message vs activity asset; activity unwired) · Q4=A bundled assets · Q5=A localStorage mute toggle · Q7=A feed badge out of scope · Q8=A in-app audio only (no browser Notification API).

  • src/realtime/MessageRealtime.ts — server emits message:new to both participants (no server changes in this plan)

Closest analogs

  • Follow: Plan 22 socket client patterns — listen in shell, ignore events you cannot act on, no business logic in components beyond presentation.
  • New module home: frontend/src/lib/notificationSounds.ts (playback + unlock + preference read/write) and frontend/src/hooks/useMessageNotificationSound.ts (route-aware listener). Keep UI toggle thin in Account Settings.

Constraints

Must

  • Frontend-only — no API, service, or migration changes
  • Listen on existing message:new socket event; do not add server emits
  • Respect suppress rules (self, open thread)
  • Provide mute toggle in Account Settings with localStorage persistence
  • Unlock audio after user gesture (browser autoplay policy)
  • Sound module typed for message and activity kinds even if only message is wired
  • Keep sounds short (~0.3–1.0s); moderate volume; no looping

Must Not

  • No bell/activity notification sounds in v1 (asset may ship dormant)
  • No feed-badge sounds
  • No browser Notification API / OS toasts
  • No server-persisted preferences or new npm deps
  • No sound on message:unsent, reactions, or unread-only bumps
  • No always-on polling to detect messages when socket is down

Out of scope

  • Bell notification sounds + Socket.IO notification:new push (follow-up plan)
  • Per-conversation mute, custom user-uploaded sounds, volume slider
  • Mobile push / email
  • Sounds while tab is background-only (Q2=A plays on any non-thread page, not hidden-tab-only)

Risk

Level 2 — Concern. Frontend-only, but autoplay policy and suppress-rule bugs can make the feature feel broken or annoying.

Asset licensing / size Repo hygiene Use small royalty-free clips or project-owned tones; keep each file < 50KB if possible
Follow-up plan (not this execution): Bell notification sounds require NotificationRealtime (emit on NotificationService.notify) + wiring activity sound kind. Do not scope-creep into that here.
