Compact pinned-message activity rows

Plan: plans/08072026-pinned-message-gap-fix
Execution branch: kylie/pinned-message-gap-fix → dev
Planned: 2026-08-07

Why

Pin activity is durable conversation history, but the current activity component gives each event 20px of top and bottom margin. Consecutive events therefore look like unrelated floating notices with an approximately 80–90px visual gap. Its translucent surface also varies against a vertical gradient theme, making otherwise identical events look inconsistent.

What and Done

  • Render every pin and unpin action as its own chronological timeline event; do not collapse, hide, dismiss, or aggregate repeated events.
  • Reduce consecutive pin-activity spacing to a compact 12px visual gap while preserving day separators and normal message/reaction spacing.
  • Render each activity as a plain, centered system-log line with no card, border, background, icon, or side dividers.
  • Show You pinned a message or You unpinned a message to the actor; show only the first word of the actor’s display name to every other participant.
  • Preserve the semantic role="status" and avoid changes to message, pin, socket, API, or database behavior.

Constraints

MustMust not / Out of scope
  • Use the existing theme CSS variables and no new dependency.
  • Keep visual styles in the chat stylesheet and leave the row component presentational.
  • Use plain text with theme-aware muted foreground, without card, border, background, icon, or divider styles.
  • Derive the viewer-relative label only from the existing activity actor ID and signed-in user ID.
  • Verify a gradient theme, a solid/default theme, and adjacent pin events.
  • No notification/toast system change; this is conversation history, not a toast.
  • No close control, client-side dismissed-state, animation, aggregation, or count badge.
  • No changes to pin persistence, message ordering, realtime events, API contracts, or migrations.
  • No broad thread-style refactor or change to ordinary message bubble spacing.

Risk & blast radius

Level 2 — Concern. A plain system-log line can be mistaken for message content or use the wrong actor-relative label. Mitigation: retain a centered, muted, compact treatment; compare activity.actorId with the authenticated viewer’s ID in the existing renderer; verify the actor and the other participant see their respective text.

Consumers: /messages/:conversationId through ThreadView.tsx → ThreadViewContent.tsx → MessagePinActivityRow.tsx; theme variables produced by chatThemeApply.ts; timeline ordering from threadTimeline.ts. Backend pin models, services, routes, sockets, and persistence are explicitly unaffected.
