Why and what

Dave’s review found that notification sound preferences could not be saved for activity-only use, notification counts did not propagate after every pending-count mutation, two sound domains interrupted one another, activity audio played without an explicit choice, and an open activity list could go stale.

This corrective execution makes an activity tone opt-in, permits either notification domain to be independently silent, keeps their audio elements independent, emits count changes after every in-scope mutation, and refreshes the open notifications page after a count event.

Context and blast radius

  • frontend/src/lib/notificationSounds.ts — persisted preference contract, autoplay unlock, preview and live playback.
  • frontend/src/components/NotificationSoundsSettings.tsx — Account Settings controls and save gating.
  • frontend/src/pages/NotificationsPage.tsx — activity list lifecycle while open.
  • src/realtime/NotificationRealtime.ts — user-scoped socket count emission.
  • src/services/NotificationService.ts and src/services/FriendshipService.ts — read, accept, decline, and cancellation count-changing mutations.

Closest patterns: existing message sound id is nullable and existing Socket.IO count events update the shell badge. This plan extends those contracts without a new state system, dependency, route, or migration.

Constraints

  • Keep user preference storage local-only and preserve message-sound behavior.
  • Use the existing authenticated, user-scoped notifications:count event; realtime publish failures must remain non-fatal.
  • Do not add a database migration, external API, package, browser notification permission, or polling loop.
  • Do not claim two-browser audio behavior as automated verification; leave it as a runnable acceptance step.
