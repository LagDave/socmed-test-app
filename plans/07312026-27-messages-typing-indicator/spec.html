Why

Plan 22 shipped live message delivery over Socket.IO but explicitly deferred typing and presence. In a 1:1 chat, the gap is obvious: when your friend is composing, the thread looks idle until the message lands.

A lightweight typing indicator closes that feedback loop without touching the REST mutation path or schema — the natural follow-up to Plan 22’s realtime foundation.

What

When a user is actively typing in an open thread, their mutual friend (the peer in that conversation) sees an animated “typing” cue in the thread view.

Deliverables:

  • Server — First client→server Socket.IO handlers: accept typing:start / typing:stop, validate participant, relay typing:update to the peer’s user:{id} room. Ephemeral in-memory TTL (~3s) so stop events aren’t required for correctness.
  • SPA — thread — Debounced emit from the thread composer; listen for peer typing; render TypingIndicator above the composer with peer display name + bouncing dots.
  • SPA — inbox — While on /messages (no active thread), listen for typing:update and replace the conversation row snippet with “{displayName} is typing…” + dots for that row.
  • No persistence — No migration, no REST endpoints.

Visual intent:

Alex is typing

Done when:

  • Two mutuals in separate browsers on the same open thread: typer’s keystrokes show the animated indicator on the peer within ~500ms while socket is connected
  • Indicator clears on stop (blur / clear / send) or server TTL expiry (~3s)
  • Typer never sees their own indicator; non-participants never receive relay
  • Inbox list shows typing snippet on the matching row while peer types (even when thread is not open)
  • Disconnected socket: no typing indicator (messages poll fallback unchanged)
  • No schema migration; no new npm dependencies
  • Typecheck/build green; acceptance rollup Passed or waived in writing

Locked Decisions

#TopicChoiceWhy
1 Transport A — Socket.IO client→server for typing; server→client relay only to peer Ephemeral signal; doesn’t violate Plan 22’s “REST writes” rule for messages. Reuses existing auth + user rooms.
2 Placement A — Above composer, inside thread card (below scroll area) Messenger/iMessage pattern; visible while reading recent messages. Header subtitle rejected — too easy to miss.
3 Inbox scope B — Open thread + inbox list snippet override while peer is typing Grill lock (2026-07-31): user wants typing visible from inbox, not thread-only.
4 Animation A — Three bouncing dots + “{displayName} is typing” muted text Universal chat affordance; CSS-only, no Lottie/asset deps.
5 State storage A — In-memory Map on Node process + TTL auto-expire PM2 single instance (Plan 22 fact); typing is discardable. No Redis.
6 Timing A — Client: emit start after ~300ms debounce; heartbeat refresh every ~2s while typing; emit stop on blur/clear/send. Server: TTL ~3s per (conversationId, userId). Limits chatter; TTL covers dropped stop events.
7 Event names A — C→S: typing:start, typing:stop. S→C: typing:update Namespaced like existing message:* events; single relay event keeps client listener simple.
8 Execution branch A — kylie/messages-typing-indicator from current dev Branch already created for this feature.

Closest analogs

  • New pattern: First client→server socket events. Keep handlers thin: validate → relay → TTL. No business logic in React beyond debounce/emit.

Event contract

EventDirectionPayloadBehavior
typing:start Client → Server { conversationId: string } Validate UUID + participant; refresh TTL; emit typing:update to peer with isTyping: true
typing:stop Client → Server { conversationId: string } Clear entry; emit typing:update to peer with isTyping: false
typing:update Server → Client { conversationId: string; userId: string; isTyping: boolean } Peer updates local state if conversationId matches open thread and userId !== self

Server must never io.emit globally. Ignore malformed payloads silently (debug log only).

Constraints

Must

  • Reuse existing Socket.IO connection (getMessagesSocket / useMessagesSocket)
  • Validate conversationId + participant before relay (same gate as REST)
  • Emit only to the other participant’s user:{id} room
  • Clear typing on send, blur, empty composer, and server TTL
  • Extract UI into TypingIndicator.tsx; emit/listen logic in useTypingIndicator.ts hook
  • Mirror event constants in frontend/src/api/socket.ts and server realtime module
  • Constitution layering: no DB in socket handlers beyond ConversationModel.findById; no REST endpoints for typing

Must Not

  • No schema migrations
  • No Redis / multi-instance adapter
  • No typing in AppShell nav badge or notifications
  • No typing over REST poll fallback
  • No new npm dependencies
  • No show-self typing indicator
  • No moving message send onto socket events

Out of scope

  • Online/presence (“last seen”, green dot)
  • Group chat typing (only 1:1 today)
  • Push notifications for typing
  • Typing in AppShell nav badge / notifications bell
  • Horizontal scale / sticky sessions

Risk

Level 2 — Concern. Introduces the first client→server socket handlers, but blast radius is limited to ephemeral UI in one thread surface.

HazardBlast radiusMitigation
Relay to wrong user Privacy / confusion Participant check via ConversationModel; emit only to computed peerId; never broadcast
Socket event spam Server CPU / noise 300ms debounce + 2s heartbeat cap while typing; ignore duplicate starts within TTL window
Stuck “typing…” UI UX annoyance Server TTL ~3s; client clears on message:new from peer; stop on send/blur
Logic in React component Maintainability drift Dedicated useTypingIndicator hook; presentational TypingIndicator only
Disconnected socket Feature absent offline Accepted v1 limitation — same as Plan 22 poll fallback scope; document in acceptance A6
Pushback: Do not add Redis, nav-badge typing, or REST endpoints in this execution. Inbox row snippet override is in scope per grill; global badge typing is not.
