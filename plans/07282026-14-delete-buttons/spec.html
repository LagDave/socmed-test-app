Why

Authors can create posts, comments, and replies but cannot remove them from the UI. Backend owner-delete already exists; the SPA never calls it. Users need a clear, confirmed way to remove their own content.

What

  • Add a Delete control on the author’s own posts (Feed + post detail), comments, and replies (post detail).
  • Every delete asks for confirmation first via an in-app ConfirmDialog modal (not the browser’s native confirm). Cancel aborts; Delete proceeds.
  • Wire to existing APIs: DELETE /api/posts/:id and DELETE /api/comments/:id (replies are comments).
  • After deleting a post from detail, navigate to Feed.
  • After deleting a comment/reply (or a post from Feed), refresh local list state so the item disappears.

Done when: Own posts/comments/replies show Delete; others’ do not; confirm cancel keeps content; confirm OK removes it; post-detail post delete returns to Feed; frontend typecheck/build green; no backend/API/schema changes.

Context

APIs already shipped (owner-only hard delete):

  • PostsController.remove → PostService.delete → PostModel.deleteOwned — route DELETE /api/posts/:id
  • CommentsController.remove → CommentService.delete → CommentModel.deleteOwned — route DELETE /api/comments/:id
  • DB: deleting a post cascades comments; deleting a parent comment cascades its replies (parent_id ON DELETE CASCADE).

UI today:

  • frontend/src/pages/FeedPage.tsx — post list, no Delete.
  • frontend/src/pages/PostDetailPage.tsx — post + threaded comments/replies + Reply; no Delete.
  • frontend/src/api/client.ts already has api.delete.
  • Closest analog: Friends outgoing Cancel — ghost Button size="sm" calling api.delete then reload. This plan adds confirm on top (Friends stays instant / untouched).

Ownership in UI: compare user.id from useAuth() to post.author.id / comment.author.id. Frontend hide is UX only; server remains the authority.

Constraints

Must

  • Show Delete only when the signed-in user is the author
  • Confirm before every delete (post, comment, reply) via in-app ConfirmDialog modal
  • Cancel confirm → no API call; content unchanged
  • Post delete on Feed + post detail; comment/reply delete on post detail
  • After post delete on detail → navigate to / (Feed)
  • Reuse existing api.delete endpoints; no new routes
  • Match existing Button patterns (prefer variant="ghost" size="sm")

Must Not

  • No backend / migration / schema changes
  • No soft delete, undo, recycle bin
  • No uploaded-file / media GC
  • No letting post authors delete other people’s comments
  • No admin / moderator delete
  • No new npm dependencies or modal libraries (use a small local ConfirmDialog)
  • Do not use native window.confirm / browser alert chrome
  • Do not change Friends Cancel behavior

Out Of Scope

  • Edit post/comment
  • Bulk delete
  • Toast / custom modal design system beyond a local ConfirmDialog
  • Optimistic UI beyond remove-after-success + reload/navigate
Decisions locked: author-only · confirm all deletes via in-app modal (not window.confirm) · post Delete on Feed + detail · detail post delete → Feed · hard delete via existing APIs · no soft delete / undo / image cleanup · no backend changes.

Risk

Level 2 — Concern. Destructive UI over CASCADE deletes; confirm is the primary mitigation. Backend already enforces ownership — frontend must not invent new authz.

HazardBlast radiusMitigation
Accidental post delete removes all comments/replies Whole post thread In-app ConfirmDialog before API; clear copy (“Delete this post?”)
Deleting parent comment cascades replies That comment’s reply thread Confirm; same Delete control; rely on existing DB CASCADE (no special UI cascade logic)
Showing Delete on others’ content (UX leak) Confusion / failed API calls Gate on user?.id === author.id; server still rejects non-owners
Stale UI after delete Ghost rows until refresh Reload list / navigate away after success; surface API errors

Consumers / blast radius: FeedPage, PostDetailPage. Existing delete services/models/routes unchanged. Friends Cancel untouched.

Required pushback (honored): Do not expand to “post author can moderate comments” or soft-delete in this plan.

Tasks

T1 — Delete own posts (Feed + detail)

Do
On FeedPage and PostDetailPage, when user?.id === post.author.id, render a Delete button. On click: open in-app ConfirmDialog (“Delete this post?”). Cancel closes with no API call. On confirm: await api.delete(`/api/posts/${id}`). Feed: reload feed (or remove that item from state). Detail: navigate("/") (use useNavigate). Show existing error pattern on failure. Do not show Delete for others’ posts.
