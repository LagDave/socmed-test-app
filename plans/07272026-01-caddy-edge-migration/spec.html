Why

alloro-asia currently terminates TLS with Apache for a single vhost (dev-asia.getalloro.com → :3000). The socmed hosts need the same edge, and the owner wants Caddy as the only public reverse proxy on this server.

What

Replace Apache with Caddy without reinstalling Signals. PM2 apps, Postgres, and Redis stay. Done when HTTPS for dev-asia.getalloro.com works through Caddy and Apache is gone.

Context

Server: SSH host alloro-asia (168.144.128.47). App: /var/www/signals (PM2 signals-backend, minds-worker). Existing LE cert: /etc/letsencrypt/live/dev-asia.getalloro.com/ — Caddy may re-issue via ACME; leave LE files in place until cutover is stable.

Analog: current Apache ssl vhost (ProxyPass + SSE Location + socket.io WS).

Constraints

Must

  • Preserve SSE flush behavior for /api/minds/
  • Preserve WebSocket for /socket.io/
  • Brief maintenance window only; document exact stop/start order
  • Validate Caddyfile before stopping Apache

Must Not

  • Restart or redeploy Signals unless required to fix proxy headers
  • Touch Postgres/Redis data
  • Add socmed host blocks yet (that is plan 09)
  • Change DNS for any domain

Out Of Scope

  • socmed.* Caddy sites (plan 09)
  • DNS record changes (human)
  • Signals application code changes

Risk

Level 4 — Major Impact. Public edge for Alloro Asia-dev goes down during cutover. Blast radius: only dev-asia.getalloro.com (confirmed sole Apache vhost). Mitigation: pre-validated Caddyfile; keep Signals up; rollback = reinstall/enable apache2 + a2ensite if Caddy fails within window.
