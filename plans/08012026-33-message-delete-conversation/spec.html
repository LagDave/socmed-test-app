Why

Users can unsend individual messages, but there is no way to remove a whole chat from the inbox. Messenger-style delete conversation hides the thread for the acting user only — the peer keeps their history — and lets the chat reappear when either side sends again or the user re-opens it from a profile shortcut.

What

Per-user hide (not hard delete) with confirm dialog, available from the thread header and inbox row overflow menus.

Deliverables:

  • Schema — nullable user_a_hidden_at and user_b_hidden_at on conversations
  • API — DELETE /api/messages/conversations/:id sets the caller’s hide timestamp; participant-only; returns { ok: true }
  • Inbox filtering — hidden threads excluded from list + unread badge counts for the viewer
  • Restore rules — clear viewer hide on open/get-or-create thread; clear recipient hide on inbound message from peer
  • Realtime — refresh deleter inbox + unread via existing conversation:updated / messages:unread (deleter only; peer unchanged)
  • SPA — overflow ⋯ on thread header and inbox row → “Delete conversation” → ConfirmDialog; navigate to /messages when deleting the active thread

Done when:

  • Deleting from inbox removes the row for the acting user; peer inbox unchanged
  • Deleting from an open thread returns to inbox and hides the conversation
  • Confirm copy explains it is removed from your inbox only
  • Peer sending a new message restores the thread in the deleter’s inbox (with unread)
  • Re-opening via Messages friend picker or profile Message icon restores the thread
  • Hidden conversations do not contribute to AppShell Messages unread badge
  • Frontend + backend typecheck/build pass; acceptance checklist passes or waived in writing

Locked Decisions

#TopicChoiceWhy
1 Delete semantics Per-user hide (Messenger default) Hard-deleting the shared conversations row would CASCADE-wipe messages for both users. Hide columns match 1:1 shared-row model without a participant settings table.
2 Peer visibility Unchanged Peer keeps full thread in inbox and can still send. No socket to peer on delete.
3 Restore triggers Inbound message + explicit open Clear hide when viewer calls get-or-create, loads thread (GET …/conversations/:id), or receives a new inbound message. Matches Messenger reappearance behavior.
4 Unread while hidden Exclude from badge + inbox Hidden threads are invisible until restored; unread counts only apply to visible inbox rows.
5 UI entry points Thread header ⋯, inbox row ⋯, and swipe-to-delete ⋯ menus on thread header and inbox row (desktop + mobile). Swipe-left on inbox row reveals Delete (mobile/touch). All paths still require confirm dialog.
6 Confirm copy “Delete conversation?” Description: “This removes the chat from your inbox. [Peer name] will still have the messages.” Confirm label: Delete.
7 Empty threads Hide allowed Conversations opened but never messaged can still be deleted from inbox.
8 Unfriend interaction Out of scope Do not auto-hide on unfriend; existing stale-thread behavior unchanged.
9 Swipe gesture Swipe-left on inbox row → Delete button Touch/pointer drag reveals a red Delete action behind the row (iOS/Messenger pattern). Tap Delete → same confirm dialog. Row tap-to-open still works when not swiped open. Desktop: ⋯ menu remains primary; swipe optional where pointer drag works.
10 Deferred UX Long-press and chat settings screen — not this plan Long-press overlaps swipe on mobile. Chat settings screen is heavier (new route/modal); revisit if we add mute/block/archive later.
Not in scope: “Delete for both,” archive folder, undo toast, long-press delete, chat settings screen, bulk delete, or clearing message bodies on hide.

Data Model (delta)

Migration propose 20260801140000_conversation_hide.ts (adjust if taken). Scaffold notes in migrations/.

Helper semantics (on ConversationModel):

  • hiddenAtForUser(row, userId) → timestamp or null
  • isHiddenForUser(row, userId) → boolean
  • setHidden(id, userId, at: Date) — sets the correct side column
  • clearHidden(id, userId) — nulls the correct side column

API Surface (delta)

MethodPathBehavior
DELETE /api/messages/conversations/:id Participant-only. Sets caller’s *_hidden_at to now. Returns { ok: true }. Emits deleter conversation:updated + refreshed messages:unread.

Existing endpoints — behavior changes:

  • GET /api/messages/conversations — exclude rows where viewer’s hide column is non-null
  • GET /api/messages/unread-count — same hide filter
  • POST /api/messages/conversations (get-or-create) — clearHidden for caller before return
  • GET /api/messages/conversations/:id — clearHidden for caller (opening thread restores)
  • POST …/messages — after insert, clearHidden for recipient (non-sender participant)

Constraints

Must

  • Hide is per-user only; peer data and inbox unchanged
  • Participant-only access on delete and all read paths
  • Confirm dialog before delete
  • Hidden threads excluded from inbox list and unread badge
  • Restore on open thread, get-or-create, or inbound message
  • Navigate to /messages when deleting the currently open thread
  • Constitution layering; no business rules in React components beyond UI state

Must Not

  • No hard delete of conversation or message rows
  • No peer notification / socket on delete
  • No archive folder or “deleted messages” admin view
  • No auto-hide on unfriend in this plan
  • No new npm dependencies without Revision Log justification

Out Of Scope

  • Delete for both users
  • Swipe gestures, bulk select, undo snackbar
  • Clearing read cursors or message content on hide
  • Blocking / reporting from delete menu

Risk

Level 2 — Concern. Inbox SQL and unread counts already use raw queries; a missed hide filter leaks “deleted” threads back into the UI or inflates the badge.

HazardBlast radiusMitigation
Hide filter omitted from one query path Deleted chats reappear; wrong unread badge Centralize “visible for user” predicate in ConversationModel; apply to inbox, unread count, and verify list endpoints
Restore clears wrong side column Peer inbox accidentally hidden Reuse user_a/user_b side mapping already used for last-read
Active thread delete leaves stale route User stuck on ghost thread URL Navigate to /messages on success; optimistic inbox removal
Inbox row overflow vs row link Accidental navigation when opening menu Stop propagation on menu trigger; keep primary row tap → thread
Migration timestamp collision Migrate failure on merge Verify unused timestamp before landing
Required pushback: Do not implement hard delete or “delete for everyone” in this plan — that is a different product contract and needs explicit approval.
