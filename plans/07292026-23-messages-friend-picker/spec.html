Why

Opening Messages with no conversations shows a dead-end empty state (“Go to Friends”). Starting a chat requires leaving Messages entirely. Users expect to see friends on the Messages surface and start a chat without bouncing to Friends or a profile.

What

On /messages (inbox), always show a Friends (new-message) section fed by accepted mutuals. Tap a friend → get-or-create conversation → open the thread. Filtering uses an icon search on the right: the text input is hidden until the search icon is tapped.

  • Mutual friends list loads automatically when the Messages inbox mounts
  • Search icon sits on the right of the Friends / New message section header
  • Tap/click icon → search input appears (auto-focus); icon acts as close (✕) while open, or Esc closes
  • Filter is client-side over mutuals (displayName + username); mutuals-only — no stranger lookup, no send-request
  • Row tap uses existing openConversationWithUsername → navigate to /messages/:id
  • Quiet “Manage friends” link (empty state and/or section footer) replaces the sole “Go to Friends” CTA
  • Conversation list unchanged below New message when inbox is non-empty
Done when: empty and non-empty inbox both expose mutuals; icon search expands/collapses correctly; picking a friend opens (or creates) a thread; no new backend endpoints.

Context

Primary file — frontend/src/pages/MessagesPage.tsx (InboxView empty state + list).

Reuse — openConversationWithUsername in frontend/src/api/messages.ts; mutuals list pattern from FriendsPage.tsx; Lucide Search / X icons already available.

Closest analog — Friends mutual rows with Message icon; this plan inverts the flow: Messages owns the friend list and opens the thread.

UI language — Existing B&W soft-card Messages canvas; ghost/icon buttons consistent with Friends message icon; no new brand accent.

Constraints

Must

  • Show mutual friends automatically on /messages inbox (empty and non-empty)
  • Search input hidden until search icon is activated
  • Search icon aligned to the right of the section header
  • Filter mutuals client-side only
  • Open chat via existing get-or-create conversation API
  • Preserve conversation list + live inbox updates (sockets/poll) behavior

Must not

  • Add friend-request / username-send UI on Messages
  • Add new backend routes or schema
  • Change thread view (/messages/:id) layout
  • Filter or hide the conversation list with the friends search (search scopes friends only)
  • Drive-by refactor of FriendsPage or AppShell

Out of scope — online presence, recent-friends ranking, pagination of mutuals, message search, groups.

Risk

Level 2 — Concern. Non-empty inbox gains a second list (friends + conversations). Mitigate with clear section titles (“New message” / “Conversations”) and keep search collapsed by default so the chrome stays light.

Blast radius — MessagesPage.tsx inbox only; consumers of conversation APIs and thread view unchanged. Friends entry icons remain valid shortcuts.

Required pushback — Do not invent a second open-conversation path; reuse openConversationWithUsername. Do not load all users — mutuals endpoint only.
