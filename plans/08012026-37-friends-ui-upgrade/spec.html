Why

Plan 16 lifted Friends from a bare scaffold, but the page still reads fragmented: the add-friend form and each list (requests, sent, mutuals) live in separate feed-card shells. Errors sit as loose text. Row density and hover affordances lag behind /notifications, which uses a single elevated card, in-card error banner, header badge, and richer empty states.

With Feed (Plan 36) and Navbar (Plan 35) upgrades in flight, Friends should match the same “social dashboard” language — without new features or API changes.

Done when:

  • Page uses one primary feed-card with internal section dividers (not 3–4 separate cards)
  • Add-friend row is the top strip inside that card (muted track + primary CTA), not a standalone card
  • Page header shows a pending-request badge when incoming.length > 0 (mirrors Notifications “X new”)
  • Errors render as an in-card banner (border-bottom + muted background), not bare paragraph text
  • Section headers keep counts; Sent Requests section still hidden when empty
  • Friend rows match NotificationRow polish: comfortable padding, hover surface, username on secondary line at sm+
  • Confirm / Decline / Cancel show icon + label at md+; Message / Unfriend stay icon buttons with accessible labels
  • Empty states use title + supporting line (like Notifications), not message-only
  • Search toggle, Esc-to-close, message navigation, unfriend confirm dialog, and all API flows unchanged
  • Light + dark parity via existing B&W tokens; prefers-reduced-motion respected
  • Frontend typecheck/build pass; acceptance checklist passes or carries written waivers
