Why

Plan 21 intentionally flattened Friends, Profile, Notifications, and Messages onto the Feed’s plain title + feed-card stack. That was correct for consistency, but Notifications lost its dashboard feel: no soft canvas plate, no hero header card with the Bell motif, and a single flat card that reads like a utility list rather than an activity center.

Dev already has strong row polish (avatars, type icons, relative timestamps, skeleton loading, nested post links, friend-request actions). The gap is page composition, not data or row logic. This plan restores the beautiful Notifications shell without undoing plan 21 globally or regressing row UX.

Re-skin /notifications with a Notifications-only soft dashboard layout while keeping every current row behavior and API call unchanged.

Context

Page today — frontend/src/pages/NotificationsPage.tsx (~276 lines): plain <section className="space-y-4"> with title outside and one feed-card overflow-hidden list. Rows are fully featured.

Reference “beautiful” snapshot — commit 8a10f69 (pre–plan-21): soft canvas, header card with Bell, separate list card, simpler rows. Use that composition; do not revert row markup to plain n.message text.

Shell — AppShell main uses mx-auto max-w-3xl px-4 py-6. Notifications canvas uses -mx-4 to bleed to main edges (same pattern as pre-21).

Tokens — frontend/src/index.css B&W variables; .feed-card uses var(--feed-shadow). Soft card shadow should match or slightly soften that elevation — prefer reusing var(--feed-shadow) before inventing new hex shadows.

API surface (unchanged) — GET /api/notifications, POST /api/notifications/read, POST /api/friends/:id/accept|decline. Header bell counts via GET /api/notifications/counts in AppShell — untouched.

Closest analog — pre-21 Notifications layout + current dev row components. No new layout primitive file required.

Blast radius — visual on /notifications only; index.css adds two classes used exclusively here.

Constraints

Must

  • Preserve all notification fetch, mark-read, and friend-action behaviors
  • Preserve nested post link semantics (rowLinksToPost / avatar link split from 686a6b5)
  • Keep B&W design tokens — no Meta blue / new brand accent
  • Scope soft canvas to Notifications route only
  • Support light and dark themes
  • Follow frontend layering — presentation in page; API via existing client (§14.x)
  • Index this plan in plans/README.md as seq 39

Must not

  • No backend, route, migration, or API contract changes
  • No new npm dependencies
  • No global body or AppShell layout rewrite
  • No soft-page restoration on Friends / Profile / Messages / Account Settings
  • No drive-by refactors of Feed or navbar badge logic
  • Do not merge or cherry-pick stale kylie/notification-page-upgrade wholesale

Out of scope

  • Notification sounds / push / realtime (see plan 34 separately)
  • Filtering tabs (All / Friends / Comments)
  • Pagination or infinite scroll
  • Batch “Mark all read” control (visit already marks read)
  • Extracting a shared SoftDashboardLayout component for other pages
