Why

The profile page today is dominated by an always-visible Edit Profile form (Full Name, Username, Bio, Profile Picture upload/URL). That leaves no room for a Facebook-style profile timeline where a user's posts appear on their profile. Editing should be secondary — reachable from the ⋯ menu — so the main profile surface can show posts.

What

Restructure /u/:username so the default view is profile header + post timeline. Move Edit Profile (Full Name, Username, Bio) behind the horizontal ⋯ menu. Remove all profile-picture editing UI. Add a backend endpoint and frontend timeline that lists posts authored by the profile user.

Done when:

  • Own profile default view shows header card + post timeline — no always-visible edit form
  • ⋯ menu includes Edit Profile; choosing it opens a modal with Full Name, Username, Bio, and Save
  • Profile picture upload, URL input, camera control, and "Remove Profile Picture" menu item are gone
  • Header avatar remains display-only (existing avatarUrl or initial fallback)
  • Bio displays in the header on public/read views; editable inside the Edit Profile modal on own profile
  • GET /api/users/:username/posts returns that user's posts (newest first, limit 30)
  • Timeline reuses Feed post-card UX: timestamp, body, image, reactions, comment link, delete on own posts
  • Other users' profiles show their timeline below the header (same card pattern)
  • Existing ⋯ items remain: View Profile, Account Settings, Copy Profile Link
  • ?view=public preview still works; edit modal not shown in public preview
  • Frontend typecheck/build pass; backend typecheck/tests pass for new endpoint

Context

Profile page today — frontend/src/pages/ProfilePage.tsx (~490 lines): monolithic page with ProfileOverflowMenu (custom dropdown), always-visible edit form when isSelf && !isPublicPreview, avatar file upload + URL field, and no posts list.

Feed analog — frontend/src/pages/FeedPage.tsx loads GET /api/feed, renders feed-card post list with ReactionBar, PostActionRow, delete via ConfirmDialog.

Backend — PostModel.listFeed({ authorIds }) already filters by author. PostService.feed combines self + mutuals; new PostService.listByUsername (or similar) scopes to one author. ProfileService / UserModel resolve username.

Routes — src/routes/users.ts owns profile reads; add posts sub-route before or after existing /users/:username (order matters — mount /users/:username/posts explicitly).

Modal pattern — frontend/src/components/ConfirmDialog.tsx for overlay, focus trap, Escape dismiss. New EditProfileDialog follows same shell; form inside.

Menu pattern — Extend existing ProfileOverflowMenu in place; add "Edit Profile" as first item.

Execution branch — kylie/profile-timeline-2 (planning on plan/07302026-27-profile-timeline worktree).

Constraints

Must

  • Preserve existing profile PATCH behavior for name/username/bio
  • Keep B&W tokens and feed-card styling
  • Follow controller → service → model layering on new endpoint
  • Route all frontend API calls through api/client
  • Support light and dark themes on modal + timeline
  • Return 404 when username not found on posts endpoint
  • Delete button only when viewer is post author (same as Feed)

Must Not

  • No profile-picture upload, URL field, or remove-picture action in UI
  • No new npm dependencies
  • No database migration (posts table already exists)
  • No compose/post form on profile page in this plan
  • No pagination/infinite scroll beyond feed's limit-30 pattern
  • No privacy-settings or mutual-only profile walls
  • No drive-by restyles of Feed, Friends, or Messages

Out Of Scope

  • Profile cover photo / banner
  • Pinning or filtering posts on profile
  • Activity log (likes/comments tab)
  • Avatar upload elsewhere (Settings stub remains unchanged)
  • Realtime timeline updates / websockets

Risk

Level 2 — Concern. Profile posts visible to all logged-in users may surprise users accustomed to mutual-only feed. Avatar removal without replacement UI leaves stale avatars until a future settings surface.
