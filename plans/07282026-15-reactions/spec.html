Why

Users can create and discuss posts but have no lightweight way to react. Plan 05 deferred likes/reactions. A small emoji reaction bar (Facebook-style) under posts and under comments/replies closes that gap without building a full engagement system.

What

  • Add reactions to posts, comments, and replies (replies are comments with parent_id).
  • Fixed set of four: like 👍, heart ❤️, haha 😂, wow 😮.
  • One reaction per user per target: picking another emoji replaces; picking the same again removes.
  • UI: default control shows the emoji only (larger); the name/label appears on hover. Hover (desktop) or press/hold (touch) expands the other three inline. Hovering an emoji plays a CSS bounce/wiggle; selecting applies it with a short pop.
  • After reacting: trigger shows your emoji; nearby show per-emoji counts for types with ≥1 (hide zeros).
  • Placement: reaction control in an action row below the post on Feed and post detail. Same compact control under each comment/reply on detail.
  • Persist in Postgres; mutate via auth APIs; embed summary on feed/post/comment payloads so the UI does not N+1.

Done when: signed-in users can set/switch/clear reactions on posts, comments, and replies; counts + viewer emoji render; picker UX matches above; typecheck/build green; acceptance checklist runnable.

Constraints

Must

  • One reaction per user per post or comment (unique constraint)
  • Exact emoji set: like / heart / haha / wow (DB enum + Zod)
  • Replies use comment reaction APIs (comment_id)
  • Action row below the post on Feed + detail; under each comment/reply on detail
  • Default visible control = Like; expand inline on hover / press
  • CSS-only emoji motion (hover wiggle + select pop); no new animation libraries
  • Show viewer emoji on trigger + non-zero per-emoji counts
  • Embed reactionSummary on PostView / CommentView list+get payloads (batched; no N+1)
  • Auth required; any signed-in user who can see the content may react
  • Before execution: rebase/merge kylie/reactions onto kylie/delete-button tip
  • Follow Code Constitution layering (Model / Service / Controller; no business logic in UI)

Must Not

  • No multi-emoji-from-same-user on one target
  • No free-text / custom emoji
  • No framer-motion or new npm deps for animation
  • No who-reacted list / modal
  • No notifications, realtime/websockets, or reaction analytics
  • No Share button; no moving Comment into the reaction row (later plans)
  • No reactions on profiles / friend requests
  • Do not invent a parallel API client pattern — use existing api.*

Out Of Scope

  • Share-post button and Comment-beside-reaction layout redesign
  • Optimistic UI beyond light local update + rollback-on-error (reload-after-success is acceptable if simpler)
  • Admin moderation of reactions
  • Reaction edit history

Table reactions

ColumnNotes
iduuid PK, gen_random_uuid()
user_id→ users.id CASCADE, not null
post_idnullable → posts.id CASCADE
comment_idnullable → comments.id CASCADE
emojinative enum reaction_emoji: like | heart | haha | wow
timestampscreated_at / updated_at
  • CHECK: exactly one of post_id / comment_id is non-null.
  • Partial unique indexes: one row per (user_id, post_id) where post set; one per (user_id, comment_id) where comment set.
  • Indexes on post_id and comment_id for count aggregation.

HTTP

MethodPathBodyEffect
PUT/api/posts/:id/reactions{ "emoji": "like"|"heart"|"haha"|"wow" }Upsert viewer reaction on post
DELETE/api/posts/:id/reactions—Remove viewer reaction on post
PUT/api/comments/:id/reactionssameUpsert on comment/reply
DELETE/api/comments/:id/reactions—Remove on comment/reply

Responses return updated reactionSummary for that target (so the client can patch local state without a full reload). 404 if post/comment missing. Validation errors use existing fail codes style.

Embedded summary on reads

Extend PostView and CommentView:

{
reactionSummary: {
  counts: { like: number; heart: number; haha: number; wow: number };
  viewerEmoji: "like" | "heart" | "haha" | "wow" | null;
}

Hydrate in Service layer with batched queries keyed by post/comment IDs when building feed, post get, and comment list. Do not query per row in a loop.
