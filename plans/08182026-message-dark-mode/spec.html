Why

Messages already participates in the application’s persisted light/dark preference, but signed-in users can reach that preference only through the profile menu. Put a clear, icon-only toggle where users are actively messaging, without creating a second theme system or changing message data.

What

Replace the current global Messages toggle with one Messenger-style display-mode switch in the inbox header beside Message settings. It controls the whole Messages route only (inbox, thread, composer, and Message settings), persists independently, and is never rendered in a conversation action strip.

Done when: the inbox-header toggle changes the whole Messages experience immediately and persists after reload; profile/global theme changes do not alter Messages; the thread has no Moon/Sun action; and frontend checks pass.

Context and closest patterns

  • frontend/src/components/ThemeToggle.tsx is the sole theme-control component. It already calls useTheme().toggleTheme(), exposes the target-mode aria-label, and uses the existing Sun/Moon icons.
  • frontend/src/contexts/ThemeContext.tsx owns the only theme state and persists it under socmed-theme; frontend/src/lib/theme.ts updates <html class="dark">.
  • frontend/src/components/messages/InboxView.tsx contains the Messages title and the existing Message settings icon action—the inbox insertion point.
  • frontend/src/components/messages/ThreadViewContent.tsx owns the thread-header action cluster and is the closest visual analog for the compact thread control.
  • frontend/src/index.css contains .messages-thread-header-action and its custom-chat-theme color treatment. The new thread control must use that same class and compact sizing.

Scope and decisions

Revised grill locked 2026-08-18: separate Messages route mode · device-derived independent first visit · Messenger-style scope across inbox, thread, composer, and Message settings · a single compact control in the inbox header only.

Must

  • Store a Messages-specific preference separate from socmed-theme and scope its CSS variables beneath the Messages route root.
  • Show one compact control in the /messages header beside Message settings; it must not appear in /messages/:conversationId.
  • Match neighboring icon control sizing and preserve useful aria-label/aria-pressed state.
  • Keep custom conversation themes readable; the app preference changes app/default surfaces while selected chat-theme styling remains intact.

Must not

  • No change to the profile/global theme preference, API endpoint, database migration, or dependency.
  • No duplicate switch in the conversation action strip.
  • No message sending, polling, socket, search, composer, or chat-theme behavior changes.
  • No global token or palette redesign; dark mode already exists.

Out of scope: a system/auto tri-state, per-conversation dark preference, server-side theme sync, and changes to the profile-menu toggle.

Required pushback — Level 2: a message-only dark setting would conflict with the established global ThemeContext and leave the same user with two competing preferences. This plan intentionally makes the control local to Messages but keeps its effect global and persistent.
