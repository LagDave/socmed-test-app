Why

The inbox currently orders every visible conversation by recent message activity. Important people can therefore disappear beneath newer conversations. The supplied reference establishes the desired interaction: use the existing inbox-row ⋯ menu to make a person a priority and keep that conversation at the top.

This is Messenger-style personal priority: it changes only the chooser’s inbox, not the peer’s inbox, message privacy, or conversation history.

What / locked behavior

  • A participant toggles Pin profile / Unpin profile from the existing inbox-row ⋯ menu. There is no pin limit.
  • Priority persists across refresh and sign-in. Every pinned conversation stays above unpinned conversations even when new messages arrive.
  • Pins use stable first-pinned-first order, then conversation ID. Current recent-message order applies only within the unpinned group.
  • Each pinned inbox row displays a visible pin icon beside the profile name. The icon is personal to the user who selected the priority.
  • The preference is scoped to the user who selected it. It does not affect the other participant, read state, delivery, messages, or profile visibility.
  • Deleting a conversation clears only that user’s priority record in the existing transaction. A later inbound or direct restore returns unpinned.
Pinned group: [first pinned] [second pinned] ... (stable) Unpinned group: [most recently active] ... (current behavior) New message activity changes only the unpinned group.

Context and boundary

  • frontend/src/components/ConversationListRow.tsx owns the shown ⋯ menu and profile-name presentation.
  • frontend/src/components/SwipeableConversationListRow.tsx owns the surrounding swipe-to-delete gesture; it remains unchanged.
  • frontend/src/components/messages/InboxView.tsx owns canonical inbox reload, socket refresh, and visible errors.
  • src/models/ConversationModel.ts owns the parameterized, single-round-trip inbox query.
  • src/services/MessageService.ts is already 774 lines. A focused ConversationPriorityService must own priority mutations; MessageService receives only delete cleanup.
  • plans/08042026-44-pinned-chats/spec.html is the closest analog. Its private inbox pin was later removed; this spec reintroduces the product direction from the current explicit request, not stale code.

Must

  • Persist caller-scoped data in PostgreSQL through migration, model, and indexed query.
  • Use routes → controllers → services → models, protected routes, typed API client, and standard response/error contract.
  • Keep the inbox query parameterized and one round trip.
  • Use the existing icon system to render a decorative visible pin beside only the pinned inbox-row name.

Must not

  • No global conversation pin field, manual ordering, pin cap, new dependency, or thread-header control.
  • No pin indicator outside the owning user’s inbox row.
  • No changes to shared message pins, messages, delivery/read state, or swipe delete.

Out of scope

  • Groups, bulk actions, archive/mute/block, notifications, search, and cross-device conflict resolution beyond idempotent storage.

Risk & required pushback

Level 3 — Structural Risk. This changes the central inbox ordering contract and reinstates a category of data deliberately removed earlier. A global flag, unscoped join, or wrong sort would expose a user’s preference to the peer or let message activity defeat priority.

Blast radiusMitigation
Both participants’ inboxesUse a conversation_pins join table keyed by user ID and conversation ID; authorize the participant before every mutation.
Every inbox reloadPin grouping and stable pin order are primary server sort terms; recent message time sorts only unpinned rows.

Resolved boundary: Priority remains a personal inbox preference. A global pin or manual rank is a different, peer-visible product contract and is excluded.
