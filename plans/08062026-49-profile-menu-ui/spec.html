Why

The avatar trigger in the completed navbar polish is clear, but the opened panel still reads as a generic three-row utility dropdown: it has no account identity, no icons, and an ambiguous “Switch mode” action. The signed-in menu is the only global place where a person can quickly confirm the active account, reach their profile, change the display mode, or leave the session.

This is a focused account-panel upgrade. The navigation bar, routes, API calls, profile-page menus, and signed-out controls are already working and are not candidates for a redesign.

What

Upgrade only the signed-in avatar dropdown in AppNavbar into a compact account panel. It retains the existing actions and semantics while adding a profile summary, meaningful action icons, current-theme-aware language, stronger action grouping, and token-based interaction states.

Done when:

  • The signed-in menu opens as an account panel with the current user’s avatar, display name, and username when available.
  • The summary is the sole route-safe link to profilePath, with a subtle chevron affordance and no nested interactive elements.
  • Profile, theme, and logout retain their existing behavior; theme copy/icon tells the user the next mode.
  • Action rows have Lucide icons, 40px-or-larger effective targets, keyboard focus, hover, and dark-mode contrast.
  • Logout remains visually destructive but is not relocated, hidden behind a confirmation, or changed at the API layer.
  • Profile-page and avatar-image menus retain their existing .profile-dropdown-* appearance and behavior.
  • Frontend typecheck and build pass; acceptance records an interactive signed-in pass in both themes.

Context and blast radius

Primary surface — frontend/src/components/nav/AppNavbar.tsx is the presentational global navbar. It receives user data, profile path, theme toggle, and logout callback from frontend/src/components/AppShell.tsx; it must not fetch or own session state.

Theme state — ThemeContext exposes the current theme plus toggleTheme. The execution should pass the current theme down from AppShell rather than infer it from DOM classes or create a second source of truth.

Shared UI — ProfileAvatar, components/ui/dropdown-menu.tsx, and the installed Lucide icon set are the closest analogs. The existing avatar is already sized by .app-navbar-profile-avatar; no size-token change is planned.

CSS consumer audit — .profile-dropdown-menu, .profile-dropdown-item, and .profile-dropdown-divider are also used by ProfilePage.tsx and ProfileAvatarMenu.tsx. The new account-panel CSS must be limited to an app-navbar-profile-menu family.

Blast radius — all authenticated routes render AppShell, so visual/accessibility regressions affect Feed, Profiles, Friends, Messages, Notifications, and Settings. The signed-out ThemeToggle + Sign in cluster is not in scope.

Constraints

Must

  • Preserve profilePath, onToggleTheme, and onLogout behavior.
  • Use existing B&W CSS variables and current motion/reduced-motion conventions.
  • Preserve Radix menu keyboard and dismissal semantics.
  • Use displayName, username, and avatarUrl already in PublicUser.
  • Update the plan index and acceptance artifacts during execution.

Must not

  • No backend, API, route, migration, auth, or storage changes.
  • No new npm dependency.
  • No edits to generic profile dropdown selectors or profile picture menus.
  • No alteration to navbar zone layout, badge behavior, or polling/socket logic.
  • No separate account-settings link, search, notification flyout, or confirmation dialog.

Out of scope

  • Profile-page overflow and avatar-photo menus.
  • Signed-out navbar design.
  • Account Settings page redesign.
  • Responsive navbar redesign, mobile drawer, or bottom navigation.

Risk and required pushback

Level 2 — Concern. This is a global, authentication-adjacent control. The appropriate response is an intentional visual refinement with zero behavioral or API expansion; future-us will hate a profile-menu restyle that quietly forks shared dropdown styling or session behavior.
