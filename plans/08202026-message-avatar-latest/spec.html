Show the peer avatar on the latest bubble in a message run

Why

In a consecutive run of incoming messages, the sender avatar currently appears beside the first bubble. The provided screenshot shows that this makes the avatar sit at the top while the most recent bubble is at the bottom. The desired chat convention is to anchor the avatar to the last (latest) bubble of that incoming run.

What

Change only the active conversation renderer so each contiguous peer-message group displays one avatar beside its final bubble. A single incoming message remains a one-message group and therefore shows its avatar. The avatar remains a link to the peer profile and retains the existing fallback, size, alignment, and accessibility label.

Done when: for a run of two or more incoming messages, the first through penultimate rows preserve their spacer and the avatar appears only on the final row; a following outgoing message, a different sender, or the existing time-gap grouping rule starts a new run.

Context and constraints

  • frontend/src/pages/MessagesPage.tsx renders ThreadView for /messages/:conversationId.
  • frontend/src/components/messages/ThreadView.tsx delegates the active timeline UI to ThreadViewContent.
  • frontend/src/components/messages/ThreadViewContent.tsx computes adjacent message grouping and passes showAvatar to MessageBubbleRow; this is the sole execution target.
  • frontend/src/lib/formatMessageDay.ts supplies messagesShareGroup, which already defines a group as the same sender within ten minutes. Reuse it; do not create another grouping rule.
  • frontend/src/components/MessageBubbleRow.tsx already renders the peer avatar or a fixed spacer based on showAvatar. Its layout and API do not need to change.

Must

  • Use the existing next-message grouping comparison to identify the final bubble in each incoming run.
  • Preserve day separators, time-gap separators, pin/system timeline boundaries, bubble radii, reactions, and outgoing-message behavior.
  • Keep the peer avatar hidden for the current user's bubbles.

Must not

  • No API, database, socket, state-management, or dependency changes.
  • No changes to MessageBubbleRow, shared grouping utilities, or the unused ConversationMessageList component.
  • No visual redesign or message sorting change.
