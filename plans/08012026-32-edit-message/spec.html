Why

Messenger already supports send, unsend, and reactions, but typos in sent text are permanent unless the user unsends the whole message. A lightweight edit action — reachable from the existing ellipsis menu on own messages — lets users fix spelling mistakes without destroying reactions or conversation context.

What

Allow the sender to edit the text body of their own, non-unsent messages. Entry point: Edit in the Radix ellipsis menu next to Unsend on own bubbles.

Deliverables:

  • Schema — nullable edited_at on messages
  • API — PATCH /api/messages/messages/:id with { body }; ownership + participant gates; returns updated MessageView
  • Realtime — message:edited socket event to both participants (mirror message:unsent)
  • SPA — Edit menu item; inline edit mode on the bubble (textarea + Save / Cancel); subtle “(edited)” label when editedAt is set

Done when:

  • Sender can open Edit from the ellipsis menu, change text, save, and both sides see the corrected body without reload
  • Peer receives the update live via socket (or poll fallback when disconnected)
  • Edited last message updates inbox snippet text automatically
  • Non-senders, unsent messages, and image-only messages cannot be edited
  • Reactions remain intact on edited messages
  • Frontend + backend typecheck/build pass; acceptance checklist passes or waived in writing

Locked Decisions

#TopicChoiceWhy
1 Edit scope Text body only Fix typos in captions and text messages. Image URL is immutable — no re-upload flow in this plan.
2 Eligible messages Own, non-unsent, with existing body text Image-only messages (no body) have nothing to edit; hide Edit for those rows. Unsent tombstones stay read-only.
3 Edit UX Inline edit in bubble Bubble swaps to a Textarea with Save / Cancel. No modal — faster for one-line typo fixes. Escape cancels; Enter submits only with modifier (match compose behavior if present).
4 Edit indicator Show “(edited)” near timestamp Standard chat affordance when editedAt is non-null. Original createdAt stays unchanged.
5 Edit history None — timestamp only No audit table or “view edit history.” Keeps scope small; unsend already soft-deletes content.
6 Time window No time limit Consistent with unsend (no expiry in current code). Add a window later if abuse appears.
7 Empty body Text-only: reject empty trim Clearing all text on a text-only message should use Unsend, not edit. Image + caption may save empty body (caption removed).
8 Menu placement Ellipsis dropdown — Edit above Unsend User request: put Edit in the existing MoreVertical menu on own bubbles.
Not in scope: editing images, editing someone else’s messages, edit notifications, or edit history. Posts/comments edit remains deferred.

Data Model

ChangeDetail
messages.edited_at Nullable timestamptz. Set on every successful body update (including re-edits). created_at unchanged.

Migration file (proposed): database/migrations/20260801140000_message_edited_at.ts — verify timestamp unused before landing.

API Surface

MethodPathBehavior
PATCH /api/messages/messages/:id Body { body: string }. Participant + sender-only. Reject if unsent, if not sender, if trimmed body empty on text-only message, if body unchanged (optional no-op return). Updates body + edited_at. Returns { message: MessageView }.

Realtime: after PATCH, emit message:edited with { message: MessageView } to both conversation participants; emit conversation:updated so inbox snippet refreshes.

Error codes: reuse MESSAGE_NOT_FOUND, MESSAGE_FORBIDDEN, MESSAGE_VALIDATION (unsent, empty body, over limit).

Constraints

Must

  • Edit only own, non-unsent messages with existing body text
  • Participant-only access (same as unsend)
  • Preserve reactions and createdAt
  • Live update for peer via socket + local patch fallback
  • Show “(edited)” when editedAt is set
  • Menu item in existing ellipsis dropdown
  • Constitution layering; no business rules in React beyond presentation

Must Not

  • No image replacement or new upload on edit
  • No edit history UI or audit table
  • No editing unsent tombstones or peer messages
  • No new npm dependencies without Revision Log justification
  • No confirmation dialog for edit (Save/Cancel inline only)

Out Of Scope

  • Edit posts or comments
  • Time-limited edit windows
  • “Message was edited” push/notification rows
  • Rich-text / markdown editing

Risk

Level 2 — Concern. Narrow feature with familiar authz pattern, but wrong-party edit is a privacy bug and stale UI on the peer is a UX bug.
